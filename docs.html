01 · Overview

Overview Specification

BinaryRevisionWithProtocol is an open protocol for immutable file revisions, transactional multi-file changes, diff, restore, and crash-safe workspace projection — without requiring Git.

A Revision is one immutable state of one logical file. A RevisionSet groups revisions across one or more files into a reviewable logical transaction. FileHead points at the currently accepted revision. Workspace Projection materializes accepted state as ordinary files.

Git is not required and not replaced. Implementations can run standalone or coexist with Git or other source-control systems. Back to top

03 · .vsn Sidecar

.vsn Sidecar Specification

.vsn is a companion sidecar file that travels with its logical file and carries its revision state/history and the information required to reconstruct or locate those revisions.

file-local sidecars
project/
`-- src/
    |-- Program.cs
    |-- Program.cs.vsn
    |-- UserService.cs
    `-- UserService.cs.vsn
  • One logical file maps to one sidecar: Program.cs + Program.cs.vsn.
  • The sidecar carries FileId, revision history, revision metadata, accepted/head information, revision references, and references to content/revision data.
  • The sidecar carries revision information and references; content bytes may be embedded or held by another storage backend. The repository does not yet freeze one layout.
  • FileId is authoritative identity. Filename is not identity.
  • Rename preserves FileId; move preserves FileId.
  • The .vsn file is not the protocol itself. It is one representation/storage mechanism for the protocol; other backends can exist.
  • Design goal: copy both files to another workspace and the revision history travels with them.

04 · Revision Model

Revision Model Specification

immutability
Revision A
    |
    v
Revision B
    |
    v
Revision C
  • A Revision is one immutable state of one logical file.
  • A committed Revision is never rewritten.
  • Revisions remain addressable according to retention policy; old revisions may be purged only under documented GC rules.
  • Restore creates new revision state based on an old revision; it never mutates the source revision.
  • Workspace files are projections; FileHead represents accepted state.

05 · File Identity

File Identity Specification

FileId is the authoritative identity of a logical file. Identity is not inferred from path, filename, content hash, size, timestamp, similarity, or delete/create proximity.

rename preserves identity
src/A.cs
    |
    v rename
src/B.cs
    FileId unchanged
move preserves identity
src/A.cs
    |
    v move
tests/A.cs
    FileId unchanged

Deleting one file and creating another with identical bytes does not automatically make them the same logical file.

  v

PENDING_REVIEW --> REJECTED
ACCEPTING -----> CONFLICTED
DRAFT ---------> ABORTED

SEALED is not a public RevisionSet state. RECOVERY_REQUIRED is not a RevisionSet state; recovery belongs to ApplyTransaction. Sealing is an operation, not a state.

07 · Content Model

Content Model Specification

references
Revision
   |
   `-- ContentRef
          |
          `-- Content Object / Storage
  • ContentRef identifies raw logical bytes by SHA-256 and exact byte size.
  • Canonical form: sha256:<64 lowercase hexadecimal characters>.
  • Hash is computed over raw file bytes before compression, encryption, or storage transformations.
  • Binary-safe: arbitrary bytes are first-class. No newline or encoding normalization.
  • LF and CRLF remain distinct byte sequences; BOM remains content; invalid UTF-8 is not silently replaced.
  • ContentRef is authoritative for identity; DiffArtifact is derived.

08 · Diff

Diff Specification

derived comparison
Revision A
    |
    +-- Compare --+
    |             |
    v             v
Revision B --> DiffArtifact
  • DiffArtifact is derived, reproducible, and disposable. It is never canonical revision state.
  • Restore does not depend on DiffArtifact for reconstructing the source revision.
  • Exact diff modes are not frozen in this repository yet; document them only when implemented.

09 · Restore

Restore Specification

  • Intended scopes: CONTENT_ONLY, CONTENT_AND_PATH, FULL_STATE.
  • Restore points at a source revision and creates new state; it never rewrites the source.
  • Restore reconstructs from revision content, not from DiffArtifact.
  • Scope/source matrix, ABSENT behavior, and failure rules are not frozen yet; no implementation found in this repository.

10 · ApplyTransaction

ApplyTransaction Specification

RevisionSet is the logical change transaction. ApplyTransaction is the physical workspace projection and recovery transaction.

intended states
PREPARING -> PREPARED -> PROJECTION_APPLYING -> PROJECTION_APPLIED
  -> LOGICAL_COMMITTING -> LOGICALLY_COMMITTED -> FINALIZED
ROLLING_BACK -> ROLLED_BACK
* -> RECOVERY_REQUIRED (physical recovery only)

11 · Crash Recovery

Crash Recovery Specification

commit marker rule
LogicalCommitMarker absent
    -> accepted state remains old
    -> rollback projection

LogicalCommitMarker present
    -> accepted state is new
    -> roll forward projection
    -> finalize

RECOVERY_REQUIRED is a physical ApplyTransaction recovery state, not a RevisionSet state. It is not evidence that a RevisionSet was accepted or rejected.

12 · Logical Commit

Logical Commit Specification

acceptance invariant
RevisionSet = ACCEPTED
        <=>
Logical Commit exists

Logical commit updates canonical accepted state (FileHeads, path index, WorkspaceVersion, LogicalCommitMarker, accept idempotency result). Physical projection finalization is separate cleanup.

Conflict path: ACCEPTING -> conflict -> CONFLICTED. No logical commit, FileHeads unchanged, partial projection rolled back.
