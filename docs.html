Core principle. BRP defines protocol semantics, canonical data representation, binary encoding rules, revision semantics, transactional semantics, integrity rules, compatibility rules, and conformance requirements. .vsn is a standardized self-contained container representation of BRP revision data — it is not the protocol itself. Libraries are implementations of BRP; applications consume BRP libraries. No implementation is authoritative over the specification.

VSN Mode. A VSN container selects one of exactly two modes — MODERN (Vertical Representation) or ENTERPRISE (Horizontal Representation). The mode determines the resource-consumption architecture for persisted content, not library capability. See Section 11.

Why two modes

Different deployments have different resource constraints. Some can spend storage so that recovery is as straightforward and computationally inexpensive as possible. Others prioritize storage efficiency and can afford additional reconstruction computation. VSN lets the resource architecture be selected without changing the library feature set or the semantic model.

Archival angle. Enterprise Mode offers the simplest recovery path: stored pre-materialized content, then direct materialization. That simplicity is a property of the representation, not a standalone longevity guarantee: framing, identifiers, versioning, field encoding, and recovery rules remain governed by the wider specification, and those byte-level decisions are still open (Section 53).

05 · Protocol Identity

Protocol Identity Normative — Frozen

BRP identifies itself via a magic number and version fields in the container format and canonical encoding.

The container MUST declare, in a canonical location discoverable without any derived structure and without executing any cryptographic hash algorithm: the protocol version, the container format version, and the RCMP canonical encoding version. The container signature is the 4-byte sequence 0x56 0x53 0x4E 0x2D at offset 0; the container format version is a u16be immediately following it, and the RCMP encoding version is the next u16be (Section 10, GR-01, GR-08). Both version words are mandatory and carry value 1 for VSN-1 and RCMP-1. An unknown container format version MUST be reported as an unsupported-version error and MUST NOT be reinterpreted (Section 06).

06 · Versioning

Versioning Normative — Frozen

BRP uses semantic versioning: MAJOR.MINOR.PATCH. MAJOR version changes indicate incompatible API changes, MINOR version changes add functionality in a backward-compatible manner, and PATCH version changes are backward-compatible bug fixes.

Version identifiers are registry-backed (Sections 40 and 46). Version comparison is by explicitly declared identifier, never by textual or numeric guessing. A reader that does not support a declared mandatory protocol version or container version MUST report an unsupported-version error and MUST NOT attempt to decode that container as though it were a supported version. An unknown derived structure version is not a version error: it MUST be ignored and recomputed (Section 10).

Three version axes exist and MUST NOT be collapsed into one value: protocol version, container format version, and RCMP canonical encoding version. The record-layout schema is a facet of the container format version unless a separate registry-backed axis exists. VSN Mode, Representation Identity, Representation Version, Hash Algorithm, Compression Algorithm, and Diff/Patch Algorithm are additionally distinct axes and MUST NOT be encoded in or inferred from a version word (Section 10, GR-38, GR-41). The container format version and encoding version are frozen as mandatory u16be words at fixed positions with value 1 (Section 05, GR-08); algorithm and representation identities are carried by their own declared fields.

08 · Data Model

Data Model Normative — Frozen

BRP operates on logical files identified by FileId. Each logical file has a sequence of revisions. Each revision has content, metadata, and relationships to other revisions. How revision content is physically persisted and represented is governed by the content representation mode in force (Section 11); the mode is not part of the logical data model and does not change revision or file identity.

10 · Canonical / Derived Boundary and Object Model

Canonical / Derived Boundary and Object Model Normative — Identity, Grammar, Semantics, Registries, Recovery, Byte Vectors Frozen

Canonical data is the source of truth for .vsn semantics: FileIdentity, Revision records, RevisionSet records with MembersDigest, FileHead mappings, canonical content objects addressed by canonical references, CommitMarker with Generation, and container integrity coverage. ContentHash, where present, is optional lookup and integrity metadata, not a precondition for discovering or decoding canonical data. Derived and precomputed data is acceleration data only.

  • Derived data MUST NOT alter canonical semantics and MUST NOT become a second source of truth.
  • Derived data MUST be rebuildable from canonical data; rebuilds MUST be deterministic given identical canonical input plus algorithm and version.
  • Missing derived data MUST NOT invalidate a canonically valid container.
  • Invalid derived data MUST be ignored and recomputed from canonical data.
  • Unknown derived versions MUST be ignored and recomputed from canonical data.
  • A reader MUST be able to operate from canonical data without derived acceleration.
  • Derived structures SHOULD carry type, version, algorithm identity, source canonical identity, and creation generation where the container format defines them; field encoding is Review/TBD and no values are frozen here.

Content objects live inside the .vsn container. They are discovered through the container's mandatory canonical framing and reference resolution, never through a cryptographic hash. ContentHash, where present, is optional identity, lookup, and integrity metadata (algorithm-selected, per Section 19); exact size is validation metadata and is not part of canonical object identity. Identical canonical content MAY share one stored object; multiple revisions MAY reference the same object. What may be shared instead of copied is constrained by VSN Mode (Section 11): a Horizontal Representation MAY share complete pre-materialized objects only, while a Vertical Representation MAY share components of an optimized representation. Physical location and offsets are not semantic identity. Deduplication MUST NOT alter canonical semantics and MUST NOT be required for canonical recovery. No external directory or storage convention is defined.

ObjectStore semantics (Review)

An object is a stored byte sequence inside the container. A reference is a semantic pointer, not a physical offset. Because object discovery MUST NOT depend on hashing, a reader MUST be able to resolve a reference to its stored object without executing any cryptographic hash algorithm. Where ContentHash is present it is optional identity, lookup, and integrity metadata; exact size is validation metadata and is not part of canonical object identity.

Identical canonical content MAY share one stored object. Physical offsets and layout are implementation detail and MUST NOT be treated as identity. A reference naming an absent object is a deterministic reference failure (missing object). Stored bytes whose computed digest does not match their declared digest are a deterministic integrity mismatch. Where no digest can be computed because the hash working mode or implementation is unavailable, the result is verification unavailable, not corruption. Unreachable objects MAY be reclaimed only under retention and reachability invariants; no binary layout is frozen here.

Hash working modes and hash-independent canonical semantics (Normative — Review)

The library supports exactly three hash working modes: None, BLAKE3-256, and SHA-256. These are library working modes, not three different VSN semantic formats. None means the library does not use a cryptographic hash for its working mode; it does not mean that objects have no identity.

Canonical semantic identity and canonical recoverability MUST NOT depend on ContentHash or on the availability of any cryptographic hash algorithm. ContentHash MAY be used for lookup acceleration, deduplication, integrity verification, caching, object addressing acceleration, equality shortcuts, and other explicitly derived purposes. A reader MUST NOT require execution of SHA-256, BLAKE3-256, or any other cryptographic hash algorithm merely to decode, discover, resolve, reconstruct, or recover canonical semantic data.

  • If a required hash implementation is unavailable, decoding MAY continue, canonical recovery MUST continue whenever the underlying canonical data is otherwise available, and integrity verification MUST be reported as verification unavailable rather than being treated as a decoding failure.
  • The specification MUST distinguish verification unavailable from corrupt.
  • Hash algorithms MUST NOT be silently substituted for one another. A container produced under one working mode MUST NOT be reinterpreted under another without an explicit declaration.
  • BLAKE3-256 MUST NOT be mandatory. Neither algorithm is required for canonical decoding or recovery.

Hash-mode isolation. Changing the working mode among None, BLAKE3-256, and SHA-256 MUST NOT make an otherwise valid canonical semantic state unreadable or unrecoverable. A hash-mode change MAY affect physical .vsn bytes, digest assertions, lookup metadata, deduplication results, derived indexes, derived caches, and reported verification status. A hash-mode change MUST NOT affect canonical core bytes, canonical semantic identity, or canonical recoverability. Canonical core bytes MUST remain independent of the selected cryptographic hash working mode.

Long-term recovery without historical hash algorithms (Normative — Review)

A future implementation that holds the frozen VSN specification, the bytes physically present in the .vsn, and implementations of the mandatory canonical decoding rules, but holds no implementation of SHA-256, BLAKE3-256, or any other historical cryptographic hash algorithm used by the container, MUST still recover all canonical information that is otherwise physically present and unencrypted.

Such an implementation MUST distinguish, and report distinctly, at least: decoded, recovered, verified, verification unavailable, integrity mismatch, unsupported transform, missing object, and malformed or corrupt canonical data. Missing cryptographic implementations MUST NOT be reported as unreadability unless the specification intentionally makes that algorithm part of permanent semantic identity; this specification does not.

Maximum-compatibility principle. The .vsn format is designed so that long-term semantic recovery depends on the frozen canonical VSN rules and the canonical bytes physically preserved in the container, not on the continued existence of historical optimization, hashing, diff, compression, indexing, caching, or storage-engine implementations. Where an optional transform genuinely prevents plaintext recovery — encryption without the required key — that limitation is explicit and conditional (Section 35), and it is reported as an access or decryption failure rather than as an integrity failure.

Index semantics (Review)

Revision, file, hash/object, parent/revision, reference, and snapshot/member indexes are derived acceleration data. A compatible valid index MAY be used. A missing index uses canonical fallback. An unknown-version index MUST be ignored with fallback. A corrupt index MUST be ignored and rebuilt or fallen back. Physical index representation MUST NOT be an interoperability requirement. A derived index MUST NOT be the only way to discover canonical records, and canonical record discovery MUST remain possible with every index absent.

Materialized snapshot and checkpoint semantics (Review)

A Revision is a canonical state transition and FileHead is the canonical current pointer. A materialized snapshot is derived materialized state — a distinct concept from the canonical Revision (Section 12) — and a checkpoint is derived acceleration state bound to a source Generation. Checkpoints MUST NOT be required for semantic validity, and a checkpoint MUST NOT be the only representation of canonical state. A valid checkpoint MAY be used; a missing checkpoint falls back to replay or recomputation; an unknown-version checkpoint MUST be ignored; an invalid checkpoint MUST be ignored and rebuilt. No fixed checkpoint frequency is defined; cadence is implementation strategy at SHOULD level.

Integrity architecture (Review)

Canonical integrity, derived integrity, and container integrity are distinct scopes and MUST NOT be conflated. Canonical equivalence MUST NOT depend on whether optional derived acceleration data exists. ContainerIntegrityHash covers the canonical envelope and canonical records only: derived units MUST NOT contribute to it, so an implementation with acceleration data and an implementation without it produce the same canonical container identity (Section 19, Section 44). Every integrity domain is algorithm-selected metadata rather than a fixed algorithm (Section 19); none of them is part of canonical semantic identity.

Read path (Review)

Open, then validate canonical envelope and commit state, then load compatible acceleration structures, then resolve references, then use valid precomputed state, then fall back to canonical reconstruction where necessary, then return semantic state. The normal path SHOULD avoid reconstructing information already available as valid derived state; fallback MUST remain deterministic.

Storage and compute principle (Review)

Implementations SHOULD prefer precomputed representations when they materially reduce repeated runtime computation. The choice between consuming the Computation Unit and consuming storage is expressed through VSN Mode (Section 11): Modern Mode uses the Computation Unit for representation and reconstruction, while Enterprise Mode persists edited content by full copy and consumes storage instead. Implementations MAY deduplicate identical logical data and use references instead of physically duplicating equivalent bytes within the mode rules of Section 11. Additional storage MAY be used to reduce repeated reconstruction, hashing, canonicalization, indexing, validation, and diff computation.

Self-contained canonical information takes precedence. When a choice exists between storing additional canonical or recovery information inside the .vsn and requiring a future implementation to recompute historical state through algorithms that MAY become unavailable, the format SHOULD prefer storing the canonical information. This preference MUST NOT be used to create a second source of truth: duplicated convenience data MUST NOT contradict, reinterpret, or substitute for canonical data, and a duplicate that could diverge MUST instead be classified as derived acceleration data. These are architecture principles, not mandatory wire-format requirements.

Canonical recovery chain (Normative — Review)

Canonical recovery follows this chain, and every step MUST have a normative source in this specification: .vsn bytes, then mandatory container framing, then canonical record discovery, then canonical object discovery, then reference resolution, then accepted state, then revision relationships, then file reconstruction, then raw logical content bytes.

  • A derived index MUST NOT be the only way to discover canonical records.
  • A derived manifest MUST NOT be the only way to discover canonical membership.
  • A checkpoint MUST NOT be the only representation of canonical state.
  • A derived diff cache MUST NOT be the only representation from which canonical content can be reconstructed (Section 22). Where content is stored as a Modern Mode delta-style representation, that representation and the canonical source data it names are canonical recovery data under Section 11, not derived acceleration data.
  • An external database MUST NOT be required.
  • Physical offsets, placement, block layout, and storage-engine conventions MUST NOT be required for semantic recovery.
  • No cryptographic hash algorithm MUST be required at any step of this chain.

Classification consequence. If an artifact is required for discovering canonical records, for discovering committed state, for resolving canonical references, or for reconstructing canonical content, then it MUST NOT be classified as purely derived: it MUST instead be classified as mandatory canonical or mandatory physical framing, or another normative mechanism MUST be defined for that function. Under the mandatory framing requirement below, no derived artifact is required for any of those functions.

Mandatory physical framing requirements (Normative — Frozen)

The canonical byte form of the container MUST be sufficient, without any derived structure and without executing any cryptographic hash algorithm, to: enumerate canonical records; identify record boundaries; identify record types; identify record lengths; skip unknown or unsupported derived units safely; locate canonical content objects; and resolve canonical references. The concrete framing, record type encoding, length encoding, and reference encoding remain freeze blockers (Section 53) and MUST NOT be treated as frozen.

Skipping MUST be safe: an unrecognized derived unit MUST be skippable from its own declared extent, and failure to skip it MUST NOT be reported as canonical corruption. Index-free recovery is therefore a mandatory property of the framing, not only an architectural intention.

ObjectSerial (canonical content object identity)

  • ID-01 — Definition. ObjectSerial is the persistent canonical identifier of exactly one canonical content object within one VSN container. It names the object; it is not a name derived from the object's bytes.
  • ID-02 — What it is not. ObjectSerial MUST NOT be a physical offset, block number, record number, record ordinal, array index, cryptographic hash, checksum, digest, generated lookup key, or implementation-private identifier.
  • ID-03 — Independence. ObjectSerial MUST be independent of cryptographic hashes, physical location, physical record order, storage engine, compression, representation algorithm, and VSN Mode. Its value MUST NOT change when any of those change.
  • ID-04 — Assignment. The writing library assigns ObjectSerial. It becomes part of canonical state at the moment the canonical object record naming it is committed by an accepted RevisionSet (Sections 13, 15, 24), not when bytes are first computed, written, staged, or buffered.
  • ID-05 — Scope and namespace. ObjectSerial is unique within one VSN container. It is not globally unique, not per ObjectStore, not per Revision, and not per file. Two independent containers MAY assign the same ObjectSerial to different objects without conflict, because every canonical reference is interpreted within the container that carries it.
  • ID-06 — Allocation model. The specification does NOT require sequential allocation and does NOT define ObjectSerial as a record number or canonical ordinal. A writer MAY allocate monotonically within a container, or may allocate by any persistent method that satisfies uniqueness and persistence; the chosen method MUST be stable for the container lifetime. The allocation method is an implementation decision that MUST NOT be observable as canonical meaning.
  • ID-07 — Canonical ordering independence. Because allocation is not defined by physical or canonical record order, reordering, compacting, repacking, or rewriting records MUST NOT change any ObjectSerial.
  • ID-08 — No reuse. An ObjectSerial MUST NOT be reused within the lifetime of one VSN container. Deletion, reclamation, or abandonment of the object it names does not free the value.
  • ID-09 — No renumbering. Physical compaction, repacking, re-layout, compression change, index deletion, index rebuild, or storage-engine replacement MUST NOT renumber an ObjectSerial.
  • ID-10 — Rewrite within the same logical container. Rewriting a container while preserving its canonical semantic state MUST preserve every ObjectSerial and every canonical reference to it.
  • ID-11 — Export and import. Creating a new VSN container from an exported one MAY assign new ObjectSerial values, provided every canonical reference is rewritten consistently within the new container. Cross-container identity equality is therefore not guaranteed and is not required.
  • ID-12 — Existence without a hash. ObjectSerial exists, is carried, and is resolvable under every hash working mode including None. No hash algorithm is required to allocate, persist, resolve, or verify the existence of an ObjectSerial.

ObjectSerial and deduplication (identity is separate from sharing)

  • ID-13 — Sharing does not create identity. Two Revisions MAY reference one ObjectSerial for shared canonical content. Sharing is a storage decision; the shared object's identity is its ObjectSerial, never the fact that it is shared.
  • ID-14 — Hash equality is never identity. ContentHash equality MUST NOT be the sole or sufficient reason a reader may establish canonical object identity. Hash-based interning MAY be used to find candidate equivalents, but every canonical reference MUST still name an ObjectSerial present in the container.
  • ID-15 — Byte-identical content MAY be distinct objects. Two canonical content objects with byte-identical stored representation MAY carry different ObjectSerial values. This is valid; no reader may assume byte equality implies identical ObjectSerial, nor that identical ObjectSerial implies a particular representation.
  • ID-16 — Mode neutrality. In MODERN Mode an ObjectSerial may name a canonical representation consumed by the Computation Unit; in ENTERPRISE Mode it may name pre-materialized content. The identity abstraction is identical in both modes.

RevisionId (revision identity)

  • ID-17 — Definition. RevisionId is the persistent canonical identifier of exactly one Revision. A Revision is identified by the pair (FileId, RevisionId); RevisionId alone is unique within one VSN container.
  • ID-18 — Not derived. RevisionId MUST NOT be a physical offset, record position, canonical ordinal, cryptographic hash, or a value derived from a diff algorithm, timestamps, generation numbers, or record ordering.
  • ID-19 — Assignment and persistence. The writing library assigns RevisionId when the Revision is created. It becomes canonical when the Revision record naming it is committed by an accepted RevisionSet. It is permanent: it MUST survive head movement, branch creation, rename, move, deletion, compaction, re-layout, export re-import, and VSN Mode change.
  • ID-20 — No reuse. A RevisionId MUST NOT be reused within one VSN container, including after deletion of the Revision it named. Removing a file does not release its historical RevisionIds.
  • ID-21 — Relation to FileHead. A RevisionId names the Revision; the FileHead of its FileId names which Revision is currently accepted. Moving the head MUST NOT change any RevisionId.
  • ID-22 — Relation to RevisionSet. Membership in a RevisionSet is an explicit canonical fact recorded by that RevisionSet's member list (Section 13). A Revision MAY be proposed in more than one RevisionSet over its lifetime; a single RevisionSet MUST NOT contain the same Revision twice (Section 13 duplicate rule, Section 10 duplicate-member semantics).
  • ID-23 — Relation to generation. Generation orders container write transactions (Sections 17, 18). It MUST NOT be used as revision identity, MUST NOT determine parent relationships, and MUST NOT substitute for a RevisionId.
  • ID-24 — Mode neutrality. The same RevisionId names the same semantic historical state in both modes, whatever representation its ContentRef resolves to.

Revision parent relationships (canonical, explicit)

  • ID-25 — Explicit representation. Parent relationships MUST be carried explicitly as a repeatable list of parent RevisionId values on the Revision record. A reader MUST NOT infer parents from chronological order, record order, Generation, timestamps, diff chains, or hashes.
  • ID-26 — Zero parents. A Revision with an empty parent list is an initial Revision of its FileId. It is valid and MUST NOT be treated as an error.
  • ID-27 — One parent. A single parent is an ordinary linear-history edge.
  • ID-28 — Multiple parents. Multiple parents are permitted and represent branch or merge ancestry. Both a branching child set and a merge Revision are representable without additional concepts.
  • ID-29 — Ordering and duplicates. Parent order carries no meaning: the parent list is a set for semantic purposes. A repeated parent RevisionId in one Revision MUST be treated as a duplicate canonical fact and reported as a deterministic canonical validation failure.
  • ID-30 — Self-parenting and cycles. A Revision naming itself as a parent is invalid. A parent graph containing a cycle, including a transitive one, is invalid. Both MUST be reported as a deterministic canonical validation failure, never silently tolerated and never repaired by inference.
  • ID-31 — Missing or foreign parent. A parent RevisionId that names no Revision in the same container is a deterministic canonical reference failure. A parent that names a Revision belonging to another container cannot be represented, because a RevisionId is container-scoped (ID-05, ID-11).
  • ID-32 — Deleted parents. If a parent Revision is removed by retention while descendants remain, the descendant MUST retain its parent reference. Resolution then reports a deterministic canonical reference failure for that edge; history is not silently rewritten.

RevisionSetId (revision set identity)

  • ID-33 — Definition and need. RevisionSetId names exactly one RevisionSet record, which carries the group of Revisions under review or acceptance, its MembersDigest, and its state (Section 13). A distinct identifier is required because the accepted boundary and the member set are canonical facts about a group, not derivable from any member.
  • ID-34 — Scope, uniqueness, persistence. Unique within one VSN container; permanent; not derived from physical layout, member order, or hashes.
  • ID-35 — Membership. Membership is explicit in the RevisionSet record. A Revision MAY appear in more than one RevisionSet over time (ID-22); a RevisionSet MUST NOT be empty (Section 13) and MUST NOT repeat a member.
  • ID-36 — Semantic or container-local. RevisionSetId is container-local canonical identity. It survives physical relocation and container rewrite preserving semantic state (ID-10); a new container MAY assign new values on export/import (ID-11).

FileId (logical file identity) and FileHead

  • ID-37 — File identity is FileId. The identity of a logical file is FileId (Section 9). Path, name, content, timestamp, and filesystem properties are NOT file identity, and FileId MUST NOT be inferred from them.
  • ID-38 — Path is revision state. A path or name at a given Revision is PathSnapshot data carried by that Revision. Rename and move change PathSnapshot while preserving FileId and every RevisionId (Section 20).
  • ID-39 — FileHead definition. FileHead is the canonical reference naming the currently accepted Revision of one logical file: the pair (FileId, head RevisionId). It is a canonical reference, not identity; the identity belongs to the Revision.
  • ID-40 — At most one head. A logical file MUST NOT have more than one head at any time, and any FileHead record naming the same FileId more than once is a deterministic canonical validation failure.
  • ID-41 — Null head. A FileHead record MAY be absent for a FileId that has no accepted Revision yet. Absence means no accepted state; it MUST NOT be represented as a sentinel Revision, and no Revision is thereby implied.
  • ID-42 — ExpectedRevisionId is not identity. ExpectedRevisionId is an operation precondition supplied by a client at commit time (Section 14). It is not canonical stored state, not an identity, and MUST NOT appear as a second head reference.
  • ID-43 — Head movement. Changing the head changes only the FileHead's head RevisionId and the accepting Generation. It MUST NOT change any RevisionId, FileId, parent relationship, or ObjectSerial.
  • ID-44 — History stays addressable. After head movement every historical Revision of that FileId remains addressable by its own RevisionId, including Revisions no longer on the head path.
  • ID-45 — Head recovery without an index. The accepted head is recovered by reading canonical FileHead records. No index, cache, or derived structure is required, and no index location may be used as head identity.

ContentRef (canonical content reference)

  • ID-46 — Required structure. A canonical ContentRef MUST carry a required ObjectSerial. It MAY additionally carry an optional ContentHash and an optional declared size.
  • ID-47 — Optional metadata roles. ContentHash is optional verification and acceleration metadata only. Declared size is optional validation metadata only. Neither is identity, and neither may substitute for ObjectSerial.
  • ID-48 — Resolution under HashMode None. A ContentRef MUST be resolvable to its canonical content object with no cryptographic hash present, no index, no derived manifest, no physical offset, and no dependence on record order.
  • ID-49 — Resolution failure. A ContentRef naming an ObjectSerial that is absent from the container is a deterministic canonical reference failure: missing object (Section 38). It is never silently treated as empty content, and never repaired by hash lookup.
  • ID-50 — Mode-neutral resolution. Resolution yields the same abstraction in both modes: MODERN yields a canonical representation consumed by the Computation Unit; ENTERPRISE yields pre-materialized content. Downstream logical content is identical.

Duplicate, dangling, and invalid canonical identity

  • ID-51 — Duplicate ObjectSerial. Two canonical objects claiming one ObjectSerial is a deterministic canonical validation failure. A reader MUST NOT choose one by physical order, offset, or record position.
  • ID-52 — Duplicate RevisionId. Two Revision records claiming one RevisionId is a deterministic canonical validation failure.
  • ID-53 — Duplicate RevisionSetId. Two RevisionSet records claiming one RevisionSetId is a deterministic canonical validation failure.
  • ID-54 — Dangling canonical references. A canonical reference to an identifier absent from the container is a deterministic canonical reference failure, distinct from malformed bytes and distinct from verification being unavailable.
  • ID-55 — Cross-container references. A canonical reference is always interpreted within its own container. An identifier belonging to another container has no meaning in this one and, if carried, is treated as a dangling reference (ID-54).
  • ID-56 — Never implementation-defined. Every condition in ID-29, ID-30, ID-31, ID-40, and ID-51 through ID-55 MUST be reported as a distinct, deterministic failure state defined in Section 38. No such condition may be left to implementation discretion, heuristic repair, or best-effort resolution.
  • ID-57 — Validation does not depend on derived data. Duplicate and dangling detection MUST be performable from canonical records alone, without indexes, caches, or hashes.

Canonical versus derived identity classification

  • ID-58 — Canonical identities. ObjectSerial, RevisionId, RevisionSetId, FileId, FileHead, parent RevisionId, and ContentRef are canonical. They are the source of truth for recovery.
  • ID-59 — Non-identities. ContentHash, size, index mappings, cache mappings, physical offsets, block numbers, record ordinals, and materialized snapshots are NOT identity. An implementation MUST NOT treat any of them as canonical identity or as a substitute when a canonical identity is unavailable.
  • ID-60 — Identity recovery is canonical-only. The full canonical identity graph MUST be reconstructable from canonical records alone. Deleting every index, cache, snapshot, checkpoint, manifest, and diff artifact MUST NOT prevent reconstruction of identity relationships.
  • ID-61 — Physical relocation invariance. Rewriting a container with the same canonical semantic state but different record order, offsets, block placement, compression, and index placement MUST preserve every ObjectSerial, RevisionId, RevisionSetId, FileId, FileHead, and parent relationship, and MUST preserve all resolutions between them.
  • ID-62 — Reader obligation. A conforming reader MUST resolve identity relationships by canonical identity alone, and MUST NOT interpret an offset, record position, block number, or index location as canonical identity under any circumstance.

Validation order and hidden-dependency prohibitions

  • SR-39 — Feature parity. Every VSN library feature — create, open, read, write, edit, revisions, history, relationships, reconstruction, deletion, metadata, verification, canonical recovery — is semantically identical in both modes. Modes differ only in resource architecture and representation. No feature is removed, disabled, or redefined by mode choice (Section 11).
  • SR-40 — Hash independence of semantics. Under all three hash working modes (None, BLAKE3-256, SHA-256) the canonical identity graph, revision graph, FileHeads, accepted state, logical content, and every semantic equality in SR-35 MUST be identical. Hash metadata affects only verification status, acceleration, and dedup optimization, and never reference resolution (GR-35).
  • SR-41 — Normative validation order. A conforming reader validates in this fixed order, stopping at the first failure and reporting its distinct category: (1) binary decoding and framing (GR-01 to GR-53); (2) canonical record syntax and field presence including conditional presence (GR-34, SR-09); (3) canonical identity uniqueness (ID-51 to ID-53); (4) reference validity (SR-32); (5) relationship graph validity including parents and RevisionSet membership (SR-16, SR-18); (6) accepted-state and FileHead validity (SR-21 to SR-24); (7) representation support (SR-30); (8) logical content materialization (SR-29, SR-31); (9) optional verification, which never precedes or blocks steps 1 to 8. Steps 1 through 7 MUST complete before any content reconstruction is attempted, so an invalid state is rejected without reconstructing content.
  • SR-42 — Derived-data deletion safety. After deleting all indexes, caches, checkpoints, derived manifests, optional diff artifacts, physical-location hints, and optional hash acceleration data, a reader MUST still recover files, FileIds, Revisions, parent relationships, RevisionSets, FileHeads, ContentRefs, ObjectSerials, canonical content, and logical file bytes from canonical data alone (SR-43).
  • SR-43 — Derived-data deletion proof chain. Recovery follows: canonical records → canonical identity graph → canonical relationships → accepted state → canonical representation or content → logical file bytes. No step in that chain consumes an index, cache, checkpoint, derived manifest, offset map, external database, or original implementation. Any artifact whose removal would break the chain is by definition canonical recovery data and not derived (SR-02).
  • SR-44 — Physical re-layout equivalence. Reordering records, changing offsets, block boundaries, compression, index presence, or storage engine MUST NOT change canonical semantic state. Physical layout and semantic ordering are distinct, and neither is derived from the other (SR-34, GR-51).
  • SR-45 — No hidden dependencies. No canonical semantic fact may be defined by, recoverable only from, or inferable from an index, cache, diff artifact, checkpoint, physical offset, previous-Revision representation in ENTERPRISE mode, or timestamp. Where such a dependency is discovered, the depending artifact is misclassified and MUST be reclassified as canonical.

Reference validity, equality, and validation order

  • SR-32 — Reference validity classes. A canonical reference is valid, missing (names nothing in the container), foreign (names an identifier of another container), duplicate (names an identity claimed twice), cyclic (a parent cycle), or invalid (reserved zero or malformed). Missing, malformed binary, unsupported representation, and verification unavailable are four distinct outcomes and MUST NOT be reported interchangeably.
  • SR-33 — Duplicate semantics. A duplicate canonical identity is always a canonical validation failure; it is never resolved by last-wins, first-wins, position, or Generation. A repeated optional metadata field within one record is also a canonical validation failure. Repeated RevisionSet members and repeated parents remain invalid per SR-18 and ID-29.
  • SR-34 — Semantic ordering. Wire order (GR-16) and semantic order are distinct. Every collection has set semantics for equality and a canonical sorted order for encoding: parent lists, RevisionSet members, and the files, revisions, and objects of a container as sets. No collection carries sequence semantics, so reordering any of them never changes canonical semantic state (SR-16, SR-18).
  • SR-35 — Equality model. Four distinct relations apply: byte equality (identical file bytes); structural equality (identical canonical records and encodings); canonical-state equality (identical canonical semantic state, regardless of physical layout or encoding form); logical-content equality (identical logical file bytes for every file). Canonical-state equality is the interoperability relation; byte and structural equality are strictly stronger and are not required between independent writers or between modes.
  • SR-36 — Object identity versus content equality. ObjectSerial identity and logical content equality are independent. The same bytes may exist under several ObjectSerials; one ObjectSerial may serve many Revisions; equal ContentHashes do not establish identity; deduplication is optional. Only a ContentRef carrying an ObjectSerial is a canonical reference.
  • SR-37 — Cross-mode equivalence. Two states with the same canonical history, the same canonical file state, the same FileHeads, and the same logical content are semantically equivalent. Physical bytes, representation payloads, compression, record ordering, and ObjectSerial allocation across independent containers MAY differ. Only the ModeDeclaration value itself may differ between an otherwise equivalent Modern and Enterprise container.
  • SR-38 — Recovery equivalence. For a given canonical semantic state S, Recover(MODERN, S) and Recover(ENTERPRISE, S) yield identical logical file bytes. The modern path is canonical representation → Computation Unit → logical bytes; the enterprise path is canonical pre-materialized content → logical bytes. Neither path requires a hash, index, cache, checkpoint, diff artifact, compression implementation, storage engine, or external database.

ContentObject, ContentRef, and representation semantics

  • SR-26 — ContentObject meaning. A ContentObject is the canonical stored object identified by one ObjectSerial from which exactly one logical content is materialized. Many Revisions MAY reference one ObjectSerial; an object MAY exist with no referencing Revision (unreferenced but still canonical). Deleting an unreferenced object removes canonical data and is therefore not a derived-artifact deletion; it is permitted only under an explicit retention policy that preserves every referenced ObjectSerial.
  • SR-27 — ContentHash and size have no semantic effect. A declared ContentHash is verification and acceleration metadata over the logical content bytes (Section 19). Declared size is the expected length in bytes of the logical content, not of the representation payload. Absence of either is fully valid. A mismatch on a present value is an integrity mismatch about the object's content and never changes identity, membership, or head (Section 38).
  • SR-28 — Sharing is optimization. Sharing one ObjectSerial across Revisions, and holding byte-identical content in separate objects, are both semantically valid. Content equality MUST NOT be the only mechanism establishing a reference, and deduplication MUST NOT be required for recovery (ID-13, ID-15).
  • SR-29 — MODERN representation contract. A Modern object MUST carry a Representation Identity, a Representation Version, a fully declared payload extent, and any reconstruction parameters its Representation Identity requires. Reconstruction MUST be deterministic: the same canonical inputs yield the same logical bytes. A valid Modern representation MUST NOT depend on an undeclared external artifact, index, cache, or original implementation. The algorithm is not identity; an implementation MAY change its internals while preserving the declared contract and the resulting logical content.
  • SR-30 — Unsupported representation is not invalid. A well-formed object naming a Representation Identity or Version the reader does not implement yields unsupported representation. This is distinct from invalid canonical data, from malformed binary framing (GR-07), from missing object (SR-32), and from verification unavailable (Section 38). A reader MUST still decode the framing, resolve identity, and report history.
  • SR-31 — ENTERPRISE full copy. An ENTERPRISE object MUST persist the complete resulting logical content directly. It MUST NOT require a previous Revision's object, a delta, a patch, a dedup-reconstruction step, or the Computation Unit to materialize its content. Its content is canonical, not a cache, and remains recoverable when every other artifact, including all previous Revisions, is unavailable (Section 11).

RevisionSet, FileHead, and accepted state

  • SR-18 — RevisionSet meaning. A RevisionSet groups one or more Revisions, possibly across several files and several branches, for review and acceptance. Membership is canonical and explicit. A Revision MAY appear in more than one RevisionSet over its lifetime; membership order carries no meaning; a repeated member within one RevisionSet is a canonical validation failure; an empty RevisionSet is invalid because a RevisionSet with no member expresses no proposal (SR-19).
  • SR-19 — RevisionSet is not a second revision graph. A RevisionSet MUST NOT be used to infer ancestry, must not be used as an alternative parent mechanism, and MUST NOT become a hidden ordering of Revisions. Ancestry is defined solely by parent RevisionIds (SR-16).
  • SR-20 — RevisionSet state. RevisionSet state (DRAFT, PENDING_REVIEW, ACCEPTED, REVISION_REQUIRED) is canonical and orthogonal to crash recovery and physical write state (Section 13). A RevisionSet record MAY be updated only through acceptance workflows; its RevisionSetId never changes (ID-34).
  • SR-21 — FileHead means accepted. A FileHead names the accepted current Revision of one logical file. It is created when a RevisionSet containing that file's Revision is accepted, and it moves when a later accepted Revision supersedes it. Head movement changes only the FileHead and the accepting Generation; it creates no Revision and changes no RevisionId, FileId, parent edge, or ObjectSerial (SR-24).
  • SR-22 — Head may point anywhere valid. A FileHead MAY point to any historical Revision of its FileId, may move backward, and may point to a Revision on a branch. A file with no accepted state has no FileHead record; that absence is legal and means no accepted state, not an empty file. A file whose latest Revision is DELETED has no accepted current path while retaining all history (SR-10).
  • SR-23 — Accepted state is marker-based. Accepted canonical state is determined by the CommitMarker declaring the accepted Generation together with the FileHead records at or below that Generation. Recovery is marker-based and never heuristic: a reader MUST NOT infer accepted state from timestamps, file sizes, record order, or the “latest-looking” Revision (Section 17).
  • SR-24 — State classification. Canonical state distinguishes exactly: accepted (covered by the accepted CommitMarker), unaccepted (canonical records not yet covered by it, exposed only on explicit request, never as file content), incomplete (structurally truncated per GR-47), abandoned (a transaction without its LogicalCommitMarker, rolled back per Section 17), and invalid (violating a normative semantic rule in this subsection). These five MUST NOT be conflated.
  • SR-25 — Historical accessibility. After head movement or deletion, every historical Revision of the FileId remains addressable by its RevisionId, with its parent edges and ContentRef intact, using canonical data only and no index (SR-45).

File, PathSnapshot, and Revision semantics

  • SR-07 — FileId existence. A FileId names a logical file only when a FileIdentity record for it exists. A FileId referenced only by Revisions or FileHeads without a FileIdentity record is a canonical validation failure.
  • SR-08 — Revision-to-file binding. Every Revision MUST name exactly one FileId via its FileId field, and that FileId MUST have a FileIdentity record. A Revision naming two files, or none, is invalid; file membership is never inferred from path.
  • SR-09 — Presence drives content. Presence is required in every Revision. Presence PRESENT requires a ContentRef; DELETED forbids both ContentRef and PathSnapshot; DIRECTORY forbids a ContentRef and requires a PathSnapshot. A Revision violating these conditions is invalid.
  • SR-10 — Deletion is a Revision, not erasure. File deletion is expressed as a Revision with Presence DELETED whose parents are the Revision's predecessors. Deletion never erases history: all prior Revisions, their parent edges, and their ContentRefs remain canonical and addressable (SR-30).
  • SR-11 — PathSnapshot is Revision state, not identity. PathSnapshot is canonical metadata belonging to one Revision. Path is never file identity and MUST NOT be used to determine identity, membership, or parentage. Rename and move preserve FileId and every RevisionId and are expressed as a new Revision carrying a new PathSnapshot (SR-12).
  • SR-12 — Path changes create Revisions. A change of path or name is a new Revision with a new PathSnapshot and the previous Revision as parent. Two FileIds MAY carry the same PathSnapshot at different times, and two FileIds MAY have the same path concurrently; this is a path collision, reported as a distinct semantic condition, and is never resolved by merging or reassigning identity (SR-32).
  • SR-13 — Path semantics are platform-neutral. Path comparison is byte comparison of the well-formed UTF-8 PathSnapshot value (GR-26). Paths are case-sensitive, separator-sensitive, and are neither normalized nor made absolute or relative by this specification. The absolute or relative meaning of a path is determined by the client workspace, not by VSN. An empty path is invalid for a PRESENT or DIRECTORY Revision. Traversal sequences are ordinary path bytes and are validated by the client, not reinterpreted by VSN.
  • SR-14 — Revision meaning. One RevisionId identifies exactly one Revision: exactly one file, exactly one Presence, exactly one ContentRef when PRESENT, exactly one PathSnapshot when PRESENT or DIRECTORY, and an explicit parent collection. Every Revision MUST reference its FileId and, when PRESENT, its ContentRef. A Revision carries no accepted or unaccepted flag of its own: acceptance is a FileHead fact (SR-23).
  • SR-15 — Revision immutability. A committed Revision is immutable. Its RevisionId, FileId, Presence, parent collection, ContentRef, PathSnapshot, and canonical metadata MUST NOT change, and its Generation MUST NOT change, after the RevisionSet committing it is accepted. Any change of logical content or path is a new Revision. No in-place revision edit exists.
  • SR-16 — Parents are explicit and unordered. Zero parents means an initial Revision of its FileId. One parent means ordinary sequential ancestry. Two or more parents mean a merge or join point; no additional merge metadata is required or permitted to make it one. Parent order carries no meaning, so two Revisions differing only in parent order are semantically equal (SR-44). Parents are never inferred from Generation, timestamps, or record order.
  • SR-17 — Generation semantics. Generation is a canonical write-transaction ordering value, not identity. It is monotonic per container across accepted transactions. It MUST NOT equal a parent Generation plus one, MUST NOT be derived from parentage, and MUST NOT substitute for RevisionId or parent relationships. Readers MAY use it to order accepted transactions and MUST NOT require it for identity resolution. An absent optional Generation on a FileHead is semantically neutral; an invalid or non-monotonic Generation in a CommitMarker is a canonical validation failure of that acceptance, never of the Revisions it covers.

Canonical semantic rules (Normative — Frozen)

This subsection freezes the semantic layer: what the decoded canonical data means, which record combinations form a valid state, and what information is required to recover that state. It does not alter the identity model frozen as ID-01 to ID-62 or the binary grammar frozen as GR-01 to GR-53; where a semantic rule would require a binary change, that is identified as a dependency rather than applied.

The processing layers are strictly separated and MUST NOT be collapsed:

Physical Bytes -> Binary Structure -> Canonical Records -> Canonical Semantic State
                                                      -> Logical File State -> Logical File Bytes

Derived Data (independent branch, never an input to canonical state):
indexes, caches, accelerators, physical-location hints,
derived manifests, optional diff artifacts, verification accelerators
  • SR-01 — Canonical VSN state. Canonical semantic state is exactly the set of canonical records, objects, and canonical relationships sufficient to recover: the set of logical files and their FileIds; the PathSnapshot recorded per Revision; the set of Revisions with their FileId, parent RevisionIds, and ContentRefs; the set of RevisionSets with their members and state; the set of FileHeads; the canonical content objects reachable by ContentRef; the representation data required to materialize each object's logical content; and the accepted state. Anything outside that set is not canonical semantic state.
  • SR-02 — The canonical/derived boundary. An artifact is canonical if and only if removing it makes canonical semantic state unrecoverable. An artifact that can be rebuilt from canonical data alone is derived. This test, not the word “canonical”, defines the classification, and it MUST be applied by artifact rather than by record type: an optional record is not thereby derived, and a record that is physically stored is not thereby canonical.
  • SR-03 — Derived data is never an input. Derived data MUST NOT be required to establish, validate, or interpret canonical semantic state. No validation order step, no reference resolution, and no recovery step may depend on an index, cache, checkpoint, derived manifest, diff artifact, or physical-location hint.
  • SR-04 — Layer independence. Every rule in this subsection is mode-independent. VSN Mode selects representation architecture only and MUST NOT change the meaning, presence condition, cardinality, or validity of any canonical record, field, relationship, or accepted state (Section 11, GR-39).

  • VR-30 — Universal unknown-identifier rule. Every namespace classifies its own unknown values as shown. The classes are never guessed between: an unknown record is skippable because its declared length isolates it structurally, while an unknown representation identifier inside a required canonical object is not semantically ignorable (GR-29, SR-30).   • VR-31 — Reserved means reserved. A reserved value MUST NOT be assigned by any implementation, MUST NOT appear on the wire as a meaningful value, and MUST NOT be treated as implementation-defined. A reserved value encountered on the wire is malformed, or ignored where its absence is legal, as with a reserved hash algorithm identifier on an absent digest. Future versions MAY allocate a reserved value, which acquires meaning only from that version onward and never retroactively.
  • VR-32 — Lifecycle states are distinct. active (current and supported), deprecated (still fully valid; a warning may be issued; no behavior change), reserved (allocated for future use, no meaning yet), retired (no longer produced, but historically readable and never reusable), and unknown (no meaning to this reader) are five distinct states and MUST NOT be treated as synonyms. A deprecated or retired representation remains valid canonical data.
  • VR-33 — Registry ownership and collision prevention. Every registry is owned by VSN core. Ranges 0x0001–0x7FFF (0x0001–0x7F for byte-wide registries) are core-owned; 0x8000–0xFFFE (0x80–0xFE) are vendor/private; the top value of each byte-wide registry is reserved. A private identifier MUST NOT be allocated in a core range, so a future core allocation can never collide with existing private use. Collision is impossible by construction (VR-15).
  • VR-34 — Registry extension model. New entries are allocated only by appending to a registry, in ascending order, with a permanently published meaning in a later revision of this specification. Allocation is a specification act, never an online service. Writers MUST NOT emit an identifier they do not understand; readers handle unknown identifiers per VR-30. Deprecation and retirement follow VR-32, and no identifier is ever reused (VR-03).
  • VR-35 — No registry versioning layer. Registries are versioned by this specification itself; no separate registry-version field is introduced, because that would create a second hidden versioning system. An embedded or local registry snapshot is advisory implementation data and MUST NOT override a frozen identifier's published historical meaning (VR-02).
  • VR-36 — Object and declaration agreement. Where a RepresentationDescriptor exists for the (Representation Identity, Representation Version) named by an object’s ObjectDescriptor payload header, the two MUST agree. A disagreement between two canonical values, where both are otherwise well-formed and known, is INVALID_CANONICAL_STATE (0x000C) and is scoped to the containing commit. This is distinct from UNSUPPORTED_REPRESENTATION, which reports only that the reader does not implement the named identity or version (SR-30, VR-21); an object whose identity and version are known and unimplemented remains UNSUPPORTED_REPRESENTATION regardless of any declaration.
  • VR-37 — RepresentationDescriptor is optional. A RepresentationDescriptor record is optional in a canonical container; absence means no representation-level declaration is made, never that a representation is unknown or missing. An object’s interpretation, extent, and materialization MUST NOT depend on the presence of any RepresentationDescriptor record, and a representation that requires no representation-level parameter (including DIRECT-1 and EXTENTS-1 as defined in Step 6) is fully recoverable without one. Where present, a declaration is authoritative only for the representation-level values it carries and is validated per VR-36.

Recovery proof obligations

  • RC-42 — Uniqueness of accepted state. Recovery selects exactly one effective marker: among structurally complete, semantically valid markers, the one with the highest Generation, with duplicate Generations excluded as invalid. The selection is a maximum over a totally ordered set, so exactly one is selected whenever any is valid, and none is selected otherwise. Every recoverable container therefore has exactly one deterministic accepted canonical state.
  • RC-43 — No path lets the tail become accepted. Acceptance requires the selected marker to precede the data it covers physically. Any bytes after that marker are, by RC-13 through RC-15, either discarded or reported malformed, never accepted. Reordering, truncation, or corruption after the marker cannot promote them.
  • RC-44 — No artifact outside canonical data can redefine acceptance. Indexes, caches, checkpoints, manifests, digests, timestamps, physical offsets, record order, and file length are all excluded by RC-01, RC-21, RC-22, RC-23, and RC-41. Each is either derived or absent, and none participates in marker selection.
  • RC-45 — Missing data is reported, never substituted. A missing object, reference, representation, or transform is reported with its own identifier and is never replaced by another object, another algorithm, a cache, or an inferred value (VR-05, RC-29).

Recovery state machine and determinism

UNREAD
  -> STRUCTURALLY VALIDATING       [fail: MALFORMED_CONTAINER | TRUNCATED | UNSUPPORTED_*_VERSION]
  -> COMMIT BOUNDARY DISCOVERY     [fail: no valid marker -> TRUNCATED | INVALID_CANONICAL_STATE]
  -> CANDIDATE ACCEPTED STATE      (highest valid Generation marker)
  -> SEMANTIC VALIDATION           [fail: INVALID_CANONICAL_STATE | DUPLICATE_IDENTITY | INVALID_RELATIONSHIP]
  -> CANONICAL REFERENCE RESOLUTION[fail: MISSING_OBJECT | MISSING_CANONICAL_REFERENCE]
  -> TAIL CLASSIFICATION           (permitted-incomplete | permitted-uncommitted | MALFORMED_CONTAINER)

  -> RECOVERABLE                   (accepted state + materializable content)
  -> verification, optional        [VERIFICATION_UNAVAILABLE | VERIFICATION_MISMATCH]
  • RC-34 — Determinism. For identical bytes and identical declared capabilities, recovery MUST produce the same accepted state, failure class, error identifier, logical content, and verification status. No result may depend on current time, machine identity, filesystem ordering, memory layout, cache contents, network availability, registry service availability, or physical offsets (VR-07).
  • RC-35 — Resources are not semantics. Recovery requires a sequential scan of canonical records and may consume CPU, memory, and I/O. Random access, an index, or temporary workspace MAY accelerate recovery but MUST NOT be required for it, and no resource optimization may become a semantic dependency (RC-22).
  • RC-36 — Mode-independent recovery. Commit discovery, identity resolution, semantic validation, and accepted-state determination are identical in both modes. Only step 10 differs: Modern materializes through the Computation Unit, Enterprise materializes directly from pre-materialized content (SR-38). Enterprise MUST NOT silently fall back to Modern reconstruction.
  • RC-37 — Enterprise independence at recovery time. Enterprise content recovery requires no previous Revision, no diff artifact, no cache, and no index. A missing previous Revision is not an Enterprise failure (SR-31).
  • RC-38 — Modern dependencies are explicit. A Modern representation that references another canonical object or Revision does so through a declared canonical reference (VR-20, VR-24). A missing declared source yields MISSING_OBJECT; an undeclared dependency yields INVALID_CANONICAL_STATE. Modern failures are never all reported as corruption (SR-30).
  • RC-39 — Mode and version are immutable per container. A commit MUST NOT change ContainerFormatVersion, EncodingVersion, or the VSN Mode of a container; a later commit never reinterprets earlier bytes under a new encoding or a different mode. Changing mode requires export into a new container (VR-09, GR-39).
  • RC-40 — Recovery after derived-data loss and rebuild. Deleting all derived data leaves accepted state, FileHeads, the revision graph, and logical bytes unchanged; rebuilding derived data differently produces a semantically identical state and MUST NOT create new canonical identity (SR-42).
  • RC-41 — No heuristic recovery. Failure taxonomy and precedence

  • RC-29 — Six distinct failure classes. These never collapse into one another: truncated (available bytes end before a required structure completes), malformed (a complete structure violates the grammar), invalid canonical state (accepted data violates a semantic rule), missing canonical data (accepted state references canonical data that is absent), unsupported (valid state requiring an unavailable capability), and verification (digest unavailable or mismatched).
  • RC-30 — Normative recovery order. Recovery proceeds in exactly this order, stopping at the first step that fails and reporting that step's distinct error identifier: (1) signature and version words; (2) header framing and the RecordsEnd marker; (3) sequential scan of the record stream, classifying each unit as complete-valid, incomplete, or malformed; (4) collection of candidate CommitMarkers, discarding structurally incomplete or malformed ones; (5) selection of the highest-Generation structurally valid marker whose covered data is complete; (6) semantic validation of the covered canonical state per SR-41 steps 2 through 7; (7) canonical reference resolution; (8) classification of the remaining tail as permitted-incomplete, permitted-complete-uncommitted, or malformed; (9) representation support; (10) logical content materialization; (11) optional verification, which never blocks or precedes steps 1 through 10. Every branch terminates deterministically; no step falls back to an index, a cache, or a heuristic.
  • RC-31 — Earlier failures mask later ones. A condition that prevents decoding a later unit is never reported in place of the earlier, blocking failure. A truncated record is reported as truncation even if its payload would also have named an unknown representation; a malformed marker is reported as malformed even if earlier records are fine. Exactly one error identifier is reported for the blocking condition (VR-28).
  • RC-32 — Failure before versus after the effective marker. Invalid or malformed data before the effective marker invalidates the commit it belongs to and causes fallback to the previous effective marker (RC-05). Invalid or malformed data after the effective marker follows RC-13 and RC-15: incomplete bytes are a tolerated tail, complete malformed structures are a malformed container. Malformed bytes after the effective marker never become accepted state.
  • RC-33 — Failure priority matrix. The normative precedence below applies when several conditions could be reported.

Identity lifecycle across failed and abandoned writes

  • RC-24 — Identifiers allocated in an uncommitted transaction are permanently consumed. A RevisionId, ObjectSerial, RevisionSetId, or FileId allocated while writing a transaction that never reaches an effective marker remains permanently consumed for the container lifetime. It MUST NOT be reused, reassigned, or recycled, whether the transaction is abandoned, crashed, or discarded. This is required for compatibility with the Step 1 no-reuse invariants ID-08, ID-20, ID-34, and ID-37, and it is why identity lifecycle cannot depend on commit success.
  • RC-25 — Uncommitted records are canonical data but not accepted state. A complete, well-formed record physically present in an uncommitted tail is canonical data: it is retained and preserved on rewrite per GR-30, and it is not garbage. It is simply not accepted and not visible as file content (RC-08). Only a writer's explicit retention policy may reclaim unreachable bytes, and it MUST NOT reuse any identifier (RC-24).
  • RC-26 — Orphan objects. An object whose ObjectSerial no committed Revision references is canonical but unreachable. It MAY be reclaimed under retention policy, but its ObjectSerial remains consumed permanently (RC-24) and reclamation MUST NOT change any accepted state, identity, or logical content (SR-26).
  • RC-27 — No abort record required. Abandonment requires no abort record, marker, or tombstone. A reader treats an abandoned tail exactly as any other uncommitted tail. An explicit abort marker is optional and, if used, is itself just an uncommitted record with no acceptance effect.
  • RC-28 — Partial objects and records. A partially written object, Revision, or FileHead located after the effective marker is an incomplete tail (RC-13). The same structure located before any effective marker is truncation of the unaccepted region. Neither is a missing canonical object, because missing canonical object applies only to a reference from accepted state (RC-29).

Torn-write and prefix recovery rules

  • RC-11 — Truncation is never corruption. Physical end of file reached mid-unit is an incomplete tail (GR-47). It is never reported as corruption, never as a semantic failure, and never as a valid complete container.
  • RC-12 — Interruption at any byte boundary. Interruption during the magic, version word, header field, record header, record payload, field header, field value, collection, object header, object descriptor, representation descriptor, CommitMarker, or trailer yields exactly one of: a valid complete container (if the interruption point was after the trailer), or an incomplete tail discarded under RC-13. Truncation before the first effective CommitMarker yields no accepted state at all, reported as truncated (RC-24).
  • RC-13 — Permitted incomplete tail. Bytes after the effective CommitMarker that do not form complete, structurally valid canonical units are a permitted uncommitted tail. They are discarded for the purposes of accepted state, and the container is reported as recovered with an uncommitted tail present. This is the only tolerance the container grammar grants, and it is bounded by GR-48: bytes after a required terminal structure that are themselves complete and structurally valid are malformed, not a tail.
  • RC-14 — Complete uncommitted records are permitted. One or more complete, well-formed, semantically valid records physically after the effective marker are a permitted uncommitted tail, including a complete FileHead, a complete higher-Generation CommitMarker whose own covered set is incomplete, and complete objects. They MUST NOT be treated as accepted (RC-08).
  • RC-15 — Malformed uncommitted tail. A complete structure physically after the effective marker that violates the grammar is a malformed container under GR-01 to GR-04 and is reported as such. It is not silently skipped, because a reader cannot distinguish it from committed data without the marker semantics it lacks. Only incomplete bytes are tolerated after the marker (RC-13).
  • RC-16 — Committed prefix vs uncommitted tail. Given Commit A, records X and Y, Commit B, and a partial record Z, Commit B is effective if its covered set is complete and valid, and Z is discarded as an incomplete uncommitted tail. If B's covered set is itself incomplete, B is not effective, A remains effective, and every byte from X onward is uncommitted. Acceptance is never inferred from the existence of later bytes.
  • RC-17 — No rollback by discards. Discarding an uncommitted tail MUST NOT change any canonical identity, FileHead, parent edge, or ObjectSerial of the accepted state. Discarding is a read-time projection and writes nothing (SR-25, ID-43).
  • RC-18 — Phantom acceptance is impossible. A torn write cannot create an accepted state, because acceptance requires a structurally complete CommitMarker whose covered set is complete and semantically valid. No combination of partial records, partial markers, or out-of-order writes satisfies RC-01 (RC-03).

Recovery and failure semantics (Normative — Frozen)

Recovery is marker-based and deterministic. A reader MUST NOT infer accepted state from the latest record, the highest Generation, record position, file length, physical offset, timestamp, the last successfully parsed Revision, the last FileHead encountered, the largest RevisionId or ObjectSerial, the largest CommitMarker, index contents, cache contents, or checkpoint contents. Acceptance comes from the normative commit mechanism alone.

  • RC-01 — CommitMarker is the sole acceptance authority. Accepted canonical state is exactly the canonical data covered by the effective CommitMarker: the highest Generation among structurally complete, semantically valid CommitMarkers in the container. No other record, value, or artifact grants acceptance (SR-23).
  • RC-02 — What a commit covers. A CommitMarker at Generation G accepts all canonical records, objects, and FileHeads physically present before that marker. Records physically after it are uncommitted and carry no acceptance, regardless of how complete or well-formed they are.
  • RC-03 — Multiple markers are historical. Multiple CommitMarkers are permitted and are append-only. Each represents a historical accepted state. Exactly one is effective: the one with the highest Generation. Physical order alone never selects the effective marker; ties on Generation are an invalid canonical state (RC-06).
  • RC-04 — A later malformed marker never invalidates an earlier valid commit. A structurally malformed or truncated CommitMarker is discarded as an uncommitted tail. The highest valid, lower Generation marker remains effective. A later broken marker cannot retroactively damage an earlier accepted state.
  • RC-05 — A marker referencing invalid state is not effective. A structurally valid CommitMarker whose covered data violates a normative semantic rule is not effective. Recovery then selects the highest valid marker whose covered data is semantically valid, and reports the failed later commit as an invalid canonical state scoped to that commit only.
  • RC-06 — Generation reconciliation. Generation is the container-global commit sequence number, monotonic across accepted commits, and required on every CommitMarker. Gaps are permitted. Duplicate Generations are invalid. A structurally valid marker with a lower Generation than an already accepted marker is a stale marker: it is discarded and is not a rollback mechanism (RC-19). Generation never substitutes for identity (SR-17).
  • RC-07 — Transaction states. A write transaction is exactly one of: UNCOMMITTED (bytes written, no valid marker yet; well-formed but not accepted), COMMITTABLE (all canonical units complete and semantically valid, awaiting its marker), ACCEPTED (covered by the effective marker), ABANDONED (intentionally discarded; equivalent to UNCOMMITTED for all readers), or INVALID (covered by a marker but violating a semantic rule). Not-committed and invalid are distinct: an uncommitted tail may be perfectly well-formed (SR-24).
  • RC-08 — Visibility. A Revision, FileHead, or object becomes visible as file content only when covered by the effective CommitMarker. Records present without a covering marker are retrievable only on explicit request as unaccepted data and MUST NOT be reported as file content or head.
  • RC-09 — Durability is separate from acceptance. Acceptance is a VSN semantic fact established by RC-01. Persistence and durability of those bytes are storage concerns. A writer MUST NOT report a transaction as successfully committed to its caller until the commit is durable under its declared storage contract, but a reader's determination of accepted state depends only on the bytes present (RC-20).
  • RC-10 — Semantic atomicity. Atomicity is guaranteed at the VSN commit boundary, not by filesystem behavior. The specification remains correct whether the storage engine offers atomic append, non-atomic append, reordering, partial writes, delayed flush, or torn sectors, because acceptance depends only on a complete valid marker (RC-18, RC-19).

Byte-level canonicality proofs

  • BP-01 — One primitive encoding per field. Every mandatory canonical field is one of uvarint, u16be, u32be, u64be, Boolean, UTF-8 string, opaque bytes, or a 16-byte UUID, each with exactly one encoding (BV-01 to BV-11).
  • BP-02 — One integer representation. uvarint has exactly one minimal representation; the non-minimal forms 81 00 and 81 80 00 for the value 1 were both rejected, and the 10-byte overflow form was rejected (BV-04.NM2, BV-04.NM3, BV-04.OVF).
  • BP-03 — Deterministic field order. Fields are strictly ascending by FieldId; a descending order and a repeated FieldId were both rejected (IV-06, IV-07).
  • BP-04 — Deterministic collection order. Parent lists and RevisionSet members serialize ascending; encoding the same members in different input orders produced identical bytes (CV-04, CV-05).
  • BP-05 — One string form. Strings are well-formed NUL-free UTF-8 with no normalization; overlong, invalid-continuation, truncated, and embedded-NUL forms were all rejected (BV-09.4 to BV-09.7).
  • BP-06 — Deterministic reference encoding. Every canonical reference is a uvarint or a 16-byte UUID, independent of hash, offset, record order, and timestamp; the all-zero and zero-value cases are reserved and rejected (BV-10.2, IV-11, IV-12).
  • BP-07 — Deterministic digest encoding. A digest is opaque fixed-length bytes preceded by a declared algorithm identifier; the digest domain was proven by HV-02 through HV-05, where only the raw logical content reproduces the canonical ContentHash.
  • BP-08 — No offset in identity. No canonical reference is an offset. CV-01 carries the same identity graph regardless of its position, and the offset table above is an annotation only (GR-51, GR-52).
  • BP-09 — No hash in identity. CV-01 (no digest), CV-06 (SHA-256), and CV-07 (BLAKE3-256) encode the same canonical identity graph and yield identical logical content; only the optional digest fields differ (VR-17, SR-40).
  • BP-10 — Round trip. For every CV vector, Encode(Decode(B)) == B held byte-for-byte, and Recover(B) produced exactly the intended logical bytes.

Representation architecture freeze: DIRECT-1 and EXTENTS-1 (Normative — Frozen)

This subsection allocates the first two VSN core Representation Identities and freezes their contracts. It introduces no new record type, field, envelope, magic value, identity concept, or error class. Every semantic fact below is carried by an owner that already exists: the RepresentationDescriptor record type 0x0008 with fields 0x0801 Representation Identity, 0x0802 Representation Version and 0x0810 representation-level metadata (GR-41, VR-20); the operand categories of VR-23; 0x0511 declared logical size (SR-27); and the object framing of GR-12 and GR-13.

Notation: uv(n) is the minimal LEB128 uvarint of GR-21 and u16(n) is u16be (GR-22). Operand kind tags are the already-frozen VR-23 categories, encoded LITERAL_BYTES = 0, OBJECT_SOURCE = 1, NUMERIC = 2, NESTED = 3. Two distinct layers are involved and MUST NOT be conflated. A RepresentationDescriptor record (type 0x0008) is the shared declaration of one representation contract, exactly one per (Representation Identity, Representation Version), and it carries no ObjectSerial. The per-object representation data lives in that object's own ObjectDescriptor payload in the object section, which is already keyed by ObjectSerial (GR-06, GR-12). No ObjectSerial field is added to record 0x0008; field 0x0501 remains owned exclusively by ContentObject (GR-17).

DR-0 — Per-object representation payload header

Every object's ObjectDescriptor payload begins with the object's own Representation Identity (u16be) followed by its Representation Version (uv), and the remainder of the payload is the data of that representation. This satisfies SR-29 directly: a Modern object carries its Representation Identity, its Representation Version, a fully declared payload extent, and the reconstruction parameters its identity requires. The payload extent is already fully declared by ObjectLength (GR-06), so a reader locates the complete payload without executing anything and without an index. For DIRECT-1 the remainder is the logical content bytes; for EXTENTS-1 the remainder is the operation collection defined in DR-3. An empty logical content is a valid DIRECT-1 payload whose remainder is zero bytes.

DR-1 — Modern baseline representation is DIRECT-1

DIRECT-1 is the baseline representation of MODERN Mode, and DIRECT-1 is the full-content representation of ENTERPRISE Mode (GR-43, SR-31). Because the shared RepresentationDescriptor record exists exactly once per representation contract and carries no object association, a container that uses DIRECT-1 only MAY omit it entirely; a container that uses EXTENTS-1 MUST carry exactly one EXTENTS-1 declaration regardless of how many objects use it. Mode never appears in this determination and mode never forks the grammar (GR-39, GR-40). Vectors MODE-01 to MODE-04 verify all four combinations.

DR-2 — DIRECT-1 contract

Representation Identity 0x0001, Representation Version 1. After the DR-0 header, the payload bytes are exactly the logical file content bytes; there is no operation collection, no operand, and no reconstruction step. DIRECT-1 therefore has no content dependency: it depends on no previous Revision, no delta, no patch, no edit script, no hash, no index, no cache, no checkpoint, no external database, and no external service (VR-24, SR-45). Materialization is a copy and is deterministic (SR-29). Empty logical content is valid, represented by a header with a zero-length remainder, and arbitrary binary content including 00 and FF bytes is valid (GR-18). DIRECT-1 is complete and is therefore the universal complete-content fallback in both modes.

DR-3 — EXTENTS-1 contract

Representation Identity 0x0002, Representation Version 1. After the DR-0 header, the object's payload is one ordered operation collection encoded as uv(OperationCount) followed by that many operations, each a NESTED operand collection (VR-23). This collection is per object: two objects using EXTENTS-1 each carry their own collection inside their own payload, and a single shared EXTENTS-1 declaration record serves both. Each operation MUST be exactly one of the following two shapes, and no other shape is valid in this representation:

OperationOperand sequenceContributes
LITERAL(bytes)NESTED, uv(2), LITERAL_BYTES, uv(len), bytes, NUMERIC, uv(0)exactly bytes; a zero-length literal is legal and contributes nothing
COPY(sourceObjectSerial, sourceOffset, length)NESTED, uv(3), OBJECT_SOURCE, uv(serial), NUMERIC, uv(offset), NUMERIC, uv(length)materialized(sourceObjectSerial)[sourceOffset : sourceOffset + length]

The second NUMERIC in a LITERAL operation is a reserved field that MUST encode 0 in this version. Operation order is canonical and materialization is the concatenation of the operation results in that order. A source is named only by OBJECT_SOURCE; a RevisionId MUST NOT be used as a content source, and a previous Revision MUST NOT be implicit (VR-24, ID-29). The writer's choice of operations is unconstrained: this contract fixes only what a reader must be able to execute, never which algorithm produced the sequence (SR-29).

DR-4 — EXTENTS-1 dependency rules

Every referenced source ObjectSerial names a canonical ContentObject in the same container (ID-05, VR-24). Source objects are immutable for the container lifetime (ID-08, ID-10). One source object MAY be referenced by many Revisions (ID-13) and by many FileIds, so cross-file sharing is permitted wherever ObjectSerial scope permits it (ID-05, SR-28). Self-reference and any dependency cycle are invalid canonical state (SR-32, RC-29). A source absent from the container is missing canonical data, reported as MISSING_OBJECT (ID-49, ID-54). A source range MUST lie wholly within the materialized logical content of its source; otherwise the state is invalid canonical state. The dependency graph MUST be finite and acyclic; no numeric relationship between a source ObjectSerial and its target ObjectSerial is required or permitted as a semantic rule, because allocation order is not observable canonical meaning (ID-06). No dependency may be resolved through a physical offset, a hash, a cache, an index, a checkpoint, or an external service (VR-24, SR-43, GR-51).

DR-5 — Checked arithmetic

All arithmetic used to validate an EXTENTS-1 source range and the accumulated output length MUST use checked arithmetic. In particular sourceOffset + length and the running sum of operation output lengths MUST NOT wrap around. An arithmetic overflow is invalid canonical state and is reported as INVALID_CANONICAL_STATE (RC-29), never as a framing error caused by a merely malformed operand and never by introducing a new error identifier (VR-28).

DR-6 — Declared size validation

Declared logical size 0x0511 remains optional for both representations (SR-27). When it is present on an EXTENTS-1 ContentObject, the materialized output length MUST equal it; a mismatch is invalid canonical state. EXTENTS-1 does NOT require 0x0511, and vector EXT-14 verifies materialization with that field absent.

DR-7 — No canonical normalization of representation bytes

Representation encoding is not necessarily unique, but materialization is deterministic. No rule merges adjacent LITERAL or COPY operations, sorts or de-duplicates the source list, forbids an unused source, requires a minimum operation count, requires a minimum serialized size, or otherwise makes one representation byte sequence the unique form of a given logical content. The normative requirement is that the same canonical inputs yield the same logical bytes (SR-29, RC-34). Physical sharing of identical stored bytes remains valid and remains orthogonal to this rule (ID-15, SR-28).

DR-8 — Forward compatibility of the operation set

EXTENTS-1 defines exactly LITERAL and COPY. An operation a reader does not recognize MUST NOT be guessed, coerced, or skipped by an assumed length (VR-05, VR-06); it yields unsupported representation. Any future operation is allocated by a new Representation Version of EXTENTS-1 or by a new Representation Identity under the existing registry rules (VR-21, VR-13), never by silent extension of this version.

DR-9 — Resource refusal is not a canonical verdict

A reader-local resource refusal, such as exhausting its own traversal, memory, or time budget, is not a canonical validity result. It MUST NOT be reported as INVALID_CANONICAL_STATE, MUST NOT be converted into a corruption verdict, and MUST NOT by itself cause rollback to an earlier CommitMarker, because a reader that stops on its own budget has not determined the container to be invalid. It is equally not a success: the object is reported as not materialized by this reader. Canonical semantics and reader resource capacity are distinct (RC-35, RC-34), and no canonical error identifier is created for this condition (VR-28, VR-29).

DR-10 — Unsupported representation and marker acceptance

A well-framed object naming an unsupported Representation Identity or Version leaves the CommitMarker effective. SR-41 places representation support at validation stage 7 and materialization at stage 8, and SR-30 states that unsupported representation is distinct from invalid canonical data; RC-05 invalidates a marker only for a violation of a normative semantic rule, which an unsupported representation is not. Therefore no rollback to an earlier marker occurs, the framing stays decodable, and identity, graph and history continue to resolve; only that object's materialization is unsupported (GR-07, GR-42, VR-21). Vectors UREP-01 to UREP-03 verify this asymmetry against the inverse case of a genuine semantic violation.

DR-11 — Canonical versus derived under both representations

Canonical recovery data for a Modern object is exactly the ObjectSerial, the object's own Representation Identity and Version in its DR-0 payload header, its operation collection, its declared source ObjectSerial references, its literal bytes, and the declared logical size where present. Object indexes, reverse-reference indexes, dependency indexes, materialization caches, checkpoints, search indexes and compression indexes are derived (SR-42, SR-43, RC-21, RC-22). Deleting every derived structure MUST leave the accepted canonical state, the identity graph, the revision graph, and the logical file bytes unchanged. No part of DIRECT-1 or EXTENTS-1 requires any derived structure in order to be recovered.

DR-12 — Descriptor cardinality and the two ObjectSerial relationships

A RepresentationDescriptor is a shared declaration and remains exactly one per (Representation Identity, Representation Version), as frozen. Any number of objects may use that one declaration; N objects using EXTENTS-1 v1 require 1 declaration, not N. Two declarations naming the same identity and version are a duplicate and remain invalid. A declaration MUST NOT contain an ObjectSerial, an operation collection, or any other per-object data, because doing so would both breach GR-17 field ownership and convert a shared declaration into a per-object record that the frozen cardinality does not permit.

Two ObjectSerial relationships exist and MUST NOT be conflated. Relationship one, object identity: a ContentObject record and its object-section entry are keyed by ObjectSerial (0x0501, ID-46); this identifies the object itself. Relationship two, materialization dependency: an EXTENTS-1 COPY operand names a source ObjectSerial whose materialized logical bytes are copied; this is a data dependency declared by VR-24. An object carrying COPY(200, 0, 5) means object 100 uses representation EXTENTS-1 and depends on object 200 for bytes. It does not associate the shared declaration with object 100, and it introduces no dependency on any Revision, FileId, PathSnapshot, or parent relationship (ID-29, VR-24).

End of container, truncation, and trailing data (Normative — Frozen)

          
    
            
  • GR-46 — Valid EOF. A container is structurally complete only when the end-of-records marker (GR-10) has been read, the object section has been consumed to its declared end, and the trailer (GR-13) has been read completely. Reaching the physical end of the file is never by itself evidence of validity.
    • 
            
  • GR-47 — Truncation categories. Physical end of file reached mid-unit MUST be reported as a deterministic truncation failure, distinguished by where it occurred: truncated signature, truncated header, truncated field, truncated record header (partial type or partial length), truncated record payload, truncated collection, truncated object header, truncated object payload, or truncated trailer. Truncation is never reported as valid EOF and never as successful recovery.
    • 
            
  • GR-48 — Trailing bytes. After the trailer, no bytes may follow within the canonical container. Trailing bytes are malformed container. A reader MUST NOT silently ignore trailing bytes, and MUST NOT accept arbitrary garbage past the container end. This closes the former ambiguity of “reader may ignore trailing bytes”.
    • 
            
  • GR-49 — Torn-write detectability. Because every structural unit declares its own extent and the trailer declares the committed record count and Generation, an interrupted write MUST leave a structurally detectable incomplete tail. Step 2 fixes detectability only; the accept-or-discard commit semantics for a torn write are deferred to Step 5. No cryptographic mechanism is introduced here and no integrity value substitutes for structural framing (GR-14).
    • 
            
  • GR-50 — Deterministic failure separation. The grammar MUST keep these outcomes distinct and never conflate them: valid complete container; truncated container; malformed container; unsupported representation; unsupported transform; missing object; missing canonical reference; verification unavailable. Reaching physical end of file MUST NOT by itself produce “valid complete container”.
    • 
          

          
Physical independence and mode proofs (Normative — Frozen)

          
    
            
  • GR-51 — Re-layout invariance. Reordering canonical records, changing byte offsets, changing block boundaries, changing physical padding, deleting indexes, rebuilding indexes, changing storage engine, and changing compression MUST NOT change any canonical byte value, identity value, or semantic relationship. The grammar encodes extents, not positions; nothing in the grammar references an absolute offset.
    • 
            
  • GR-52 — No positional identity. Record order in the container is a physical arrangement. A reader MUST NOT derive identity, membership, or parentage from record position, record order, or offset. Semantic ordering keys (GR-19) are distinct from physical order.
    • 
            
  • GR-53 — Cross-mode semantic equivalence. Two containers holding the same semantic history MUST expose the same canonical identity graph, the same revision parent graph, the same FileHead state, and the same logical file bytes in both modes. Their physical bytes, representation payloads, compression, and layout MAY differ and are not required to match. The framing rules applied are the same GR-01 through GR-52 in both cases.
    • 
          


Mode and representation encoding (Normative — Frozen)

          
    
            
  • GR-38 — Mode declaration. Mode is declared by exactly one ModeDeclaration record (type 0x0007) in the canonical record section. Mode field 0x0701 is a u8: 0x01 MODERN, 0x02 ENTERPRISE. Values 0x00 and 0x03–0xFF are reserved. Mode is mandatory; a container lacking it is malformed.
    • 
            
  • GR-39 — Mode is not identity and does not fork the grammar. VSN Mode selects representation architecture only. It MUST NOT appear in or alter any canonical identity encoding, parent relationship, FileHead, or canonical reference (Step 1, ID-16, ID-24, ID-50). A container MUST NOT contain mixed modes: exactly one ModeDeclaration record is permitted, and a second one is malformed.
    • 
            
  • GR-40 — One grammar for both modes. Container, header, record, field, collection, object, and trailer framing are byte-identical in both modes. Only the object descriptor's representation identity and payload differ. Creating two unrelated VSN binary formats is prohibited.
    • 
            
  • GR-41 — Representation descriptor contract. A RepresentationDescriptor (type 0x0008) carries Representation Identity (0x0801), Representation Version (0x0802), and optional representation-level metadata (0x0810), and its payload is located by its own declared length. A RepresentationDescriptor is a shared declaration and MUST NOT contain an ObjectSerial or any per-object data (GR-17, VR-20). A reader MUST be able to answer, from a representation descriptor alone and without executing any algorithm and without consulting an index, which representation contract is declared, and where that descriptor’s own complete payload is. Which representation a given object uses, and where that object’s complete payload is located, MUST be answerable from the object’s own framing: the object’s Representation Identity and Version are carried in its ObjectDescriptor payload, and its complete payload extent is declared by its ObjectLength (GR-03, GR-06). Locating an object’s complete payload MUST NOT require the presence of any RepresentationDescriptor record.
    • 
            
  • GR-42 — Unknown representation identity. A descriptor naming an unsupported Representation Identity or an unsupported Representation Version MUST be reported as unsupported representation (GR-07), not as malformed framing. Descriptor framing remains fully decodable in that case.
    • 
            
  • GR-43 — ENTERPRISE payload. In ENTERPRISE Mode the object descriptor's payload MUST encode the complete persisted logical content directly as a length-delimited byte run. It MUST NOT encode a delta, a patch, a reference to a previous revision's content, or reconstruction instructions, and recovering Enterprise content MUST NOT consume the Computation Unit (Section 11).
    • 
            
  • GR-44 — MODERN payload. In MODERN Mode the object descriptor's payload MAY be a representation consumed by the Computation Unit, but its extent MUST be fully declared by the framing so that a reader can locate and skip it without reconstructing it. The framing MUST NOT be tied to one algorithm; the algorithm identity is carried by GR-41.
    • 
            
  • GR-45 — Compression is outside the grammar. Compression MAY be applied to canonical extents only where a declared compression identity says so, and a reader unable to decompress MUST report unsupported transform rather than malformed framing. Decompression MUST NOT be required to parse container, record, field, or object boundaries; compression therefore MUST NOT change any extent or identity value.
    •

  • GR-34 — Known field requiredness. A missing required field is malformed container. A present known-optional field is honored if the reader understands it and ignored if not. An absent known-optional field MUST NOT be represented by a sentinel value; absence and zero-length are distinguishable only where the field's Step 1 semantics say so, and MUST NOT otherwise be conflated.

Field framing, ordering, and collections

          
    
            
  • GR-15 — Field grammar. Every canonical field is FieldId (u16be), FieldLength (uvarint), then exactly FieldLength value bytes. A reader MUST determine a field's end from the grammar alone, never from application semantics.
    • 
            
  • GR-16 — Canonical field order. Fields within a record MUST appear in strictly ascending FieldId order, with no repeated FieldId within one record, except for fields explicitly typed as repeatable collections (GR-19). This rule is normative and is the sole ordering key; a reader MUST NOT need to guess an order.
    • 
            
  • GR-17 — FieldId namespaces. FieldIds 0x0001–0x7FFF are protocol-assigned canonical fields and MUST be unique across all record types. FieldIds 0x8000–0xFFFE are extension fields; 0xFFFF is reserved and MUST NOT be assigned. FieldId 0x0000 in a header field stream is the RecordsEnd marker (GR-09).
    • 
            
  • GR-18 — Field length limits. Maximum field value length is 264−1 bytes, bounded in practice by the enclosing record length. A field length exceeding its enclosing record extent is malformed container; one reaching physical end of file first is truncated field.
    • 
            
  • GR-19 — Collections. A repeatable collection field is encoded as a uvarint element count followed by that many fixed-grammar-encoded elements. An empty collection is a count of 0 with zero further bytes. A collection count exceeding the enclosing field extent is malformed container. Element ordering is the canonical ordering defined for that collection's Step 1 semantics: parent RevisionId lists, RevisionSet member lists, and MembersDigest input all use a total canonical order depending only on canonical member keys, never on insertion or physical order. Duplicate members remain governed by Step 1 (ID-29, ID-35) and are a deterministic validation failure, not a parse error.
    • 
            
  • GR-20 — No interior padding. Padding MUST NOT occur inside any declared extent: a field value, record payload, or object descriptor must be exactly filled by its contents. Padding, if any, exists only in the physical storage layer outside all canonical extents (GR-27).
    • 
          

          
Primitive encoding (Normative — Frozen)

          
    
            
  • GR-21 — uvarint. Unsigned LEB128, 1–10 bytes, 7 payload bits per byte, high bit set on all but the final byte, little-endian significance. The 10th byte MUST NOT set the high bit and MUST NOT contribute more than the single value bit that keeps the total within 264−1; a 10th byte with the high bit set, or contributing more than one bit, is malformed container. A multi-byte encoding with a redundant zero continuation byte (a non-minimal encoding) is malformed container on canonical read, preserving GR-24.
    • 
            
  • GR-22 — Fixed-width integers. All u16be, u32be, and u64be values are unsigned, big-endian, and fixed-width. Signed integers use two's complement with an explicit signed type name; signed values are used only where this specification names a signed field. Signedness, width, and byte order for a given field MUST NOT vary by record, mode, platform, or implementation.
    • 
            
  • GR-23 — Boolean. A canonical boolean is exactly one byte: 0x00 false, 0x01 true. Any other byte is malformed container. Booleans MUST NOT be inferred from any other value.
    • 
            
  • GR-24 — One canonical encoding per value. One canonical semantic value MUST have exactly one canonical byte encoding. Non-minimal or alternative encodings of an integer MUST be rejected on canonical read, not accepted as an equivalent form. Where a compatibility need for alternative input encodings arises in a later step, accepted input encoding MUST be distinguished from canonical emitted encoding; this specification defines no such alternative encodings today.
    • 
            
  • GR-25 — Overflow. Any length, count, or identifier exceeding its declared maximum, or a value that does not fit its declared width, is malformed container. Arithmetic overflow MUST NOT wrap, saturate, or be reinterpreted.
    • 
            
  • GR-26 — Strings. A canonical string field value is UTF-8, MUST be well-formed, and MUST NOT contain a NUL byte (U+0000). Strings MUST be byte-length delimited by FieldLength. An ill-formed UTF-8 sequence is malformed container. Unicode normalization is not applied: canonical string equality is byte equality of the well-formed UTF-8 form.
    • 
            
  • GR-27 — Physical padding is not canonical. Physical block padding, alignment slack, or storage-engine filler bytes are NOT canonical bytes and MUST NOT appear inside a container's canonical extents. Readers MUST NOT treat them as semantic data, and canonical semantic bytes MUST NOT depend on their presence or value.
    • 
          


Framing rules

          
    
            
  • GR-01 — Signature. The container MUST begin with the 4-byte signature 0x56 0x53 0x4E 0x2D (VSN-) at offset 0. A reader MUST reject any container not beginning with this signature as malformed container (Section 38). The signature is fixed-width and never variable-length.
    • 
            
  • GR-02 — Record discovery. A reader MUST be able to enumerate consecutive records by reading a 2-byte record type, a uvarint length, and that many payload bytes, without interpreting the payload.
    • 
            
  • GR-03 — Length counts payload only. Every length value (RecordLength, FieldLength, ObjectLength) counts only the bytes of its own payload or value, never its own encoding bytes and never any surrounding header bytes.
    • 
            
  • GR-04 — Nesting. A field value or record payload that contains nested structures MUST contain only structures whose extents sum exactly to the declared length. A nested extent exceeding its parent is malformed container; one falling short is also malformed container. No padding or slack is permitted inside a declared extent (GR-20).
    • 
            
  • GR-05 — Record minimum and maximum. The minimum legal record payload is 0 bytes. The maximum legal record payload is 264−1 bytes in principle, but the maximum legal container length is 263−1 bytes; a record payload length exceeding the remaining container extent is truncation.
    • 
            
  • GR-06 — Object framing is algorithm-independent. A canonical content object is framed as ObjectSerial, ObjectLength, then an ObjectDescriptor of exactly that many bytes. The framing alone MUST be sufficient to locate the complete object payload. Decoding an object descriptor MUST NOT require executing its reconstruction algorithm.
    • 
            
  • GR-07 — Unsupported representation is not malformed framing. A well-framed object whose descriptor names a representation the reader does not support MUST be reported as unsupported representation, never as malformed framing and never as a corrupt container. The framing layer MUST be fully decodable even when no representation algorithm is available.
    • 
            
  • GR-08 — Byte order. Every fixed-width multi-byte integer is big-endian (network byte order). The terms native endian, platform endian, host order, and implementation-defined MUST NOT be used for any canonical field. This applies to every record, field, and object regardless of VSN Mode, host platform, or storage engine.
    • 
            
  • GR-09 — Header and first record boundary. The header ends at the first RecordsEnd marker field (FieldId 0x0000 with zero length). The first record begins at the byte immediately following that marker. A header field stream not terminated by a RecordsEnd marker before end of container is truncated header.
    • 
            
  • GR-10 — End of container. A container ends when the first record type reads 0x0000 (end-of-records marker) and is followed by an end-of-container trailer per GR-13. Reaching physical end of file mid-unit is truncation, never valid EOF (GR-19).
    • 
            
  • GR-11 — End-of-records marker. Record type 0x0000 is reserved as the end-of-records marker. It MUST NOT be assigned to any record type and MUST carry a zero payload.
    • 
            
  • GR-12 — Objects. Objects follow the end-of-records marker in the object section. Object records are framed identically to records but keyed by ObjectSerial (Step 1, ID-01), so a ContentRef resolves with no index and no hash. An object named by a ContentRef but absent from the object section is missing object (Step 1, ID-49).
    • 
            
  • GR-13 — Container trailer. The container MUST end with a trailer carrying the canonical record count and the accepting Generation, so that a torn write leaves a structurally detectable incomplete tail (Section 24, Step 5). The canonical record count is the number of canonical records in the accepted generation, excluding the ModeDeclaration record because it is a structural mode marker carrying canonical metadata rather than a canonical state record counted by the trailer (Record role classification table). Torn-write acceptance semantics are deferred to Step 5; the framing requirement here is only that truncation be structurally detectable.
    • 
            
  • GR-14 — No record length substitution. RecordHash, ContentHash, or any integrity value MUST NOT be used in place of, or to cross-check the extent of, a structural length. Structure MUST be parseable with every hash algorithm disabled.

Wire design: container envelope semantics (Review)

The container envelope conceptually carries container identity, protocol identity, container version with its record-layout schema facet, Generation, commit state, and integrity information.

Wire design: logical container layout (Review)

The logical container is ordered as envelope, then canonical records, then the object store, then derived indexes, then snapshots and checkpoints, then the diff cache, then derived metadata.

Protocol version governs semantic rules; container version governs envelope interpretation and record layout; derived versions govern acceleration independently. A schema version is the record-layout facet of the container version and MUST NOT be treated as an independent axis unless an existing registry defines one.

Newer readers accept older canonical containers. Older readers MUST reject unsupported mandatory canonical versions with an explicit version error, and MUST ignore unknown derived units.

No version field names, values, or byte positions are frozen here.

Wire design: index key and rebuild contract (Review)

Index keys are RevisionId, FileId, ContentHash, parent RevisionId, object identity, and snapshot identity. Duplicates resolve by canonical source order.

Ordering, encoding, checksums, and versions are TBD and not frozen. Rebuild rule: same canonical container plus same algorithm and version yields a functionally equivalent index.

Wire design: materialized snapshot, checkpoint, and manifest binding (Review)

A checkpoint binds source Generation, source canonical identity, snapshot identity, and algorithm with version.

Checkpoint validity is binding equality against the canonical state the checkpoint claims to represent, not equality against the current head. A checkpoint whose claimed source state no longer matches its binding is stale and MUST be ignored; a checkpoint whose creation generation exceeds the container generation MUST be ignored; an unknown-version checkpoint MUST be ignored; a corrupt checkpoint MUST be ignored and rebuilt. Because validity is bound to the claimed source state, a checkpoint stays reusable across later generations, which is the intended storage-for-compute trade. The current container generation is explicitly not a validity criterion: a checkpoint whose source generation is 10 remains usable in a container at generation 15, provided its claimed source state still matches. A checkpoint whose claimed source state does not exist in canonical data MUST be ignored.

Manifests list members in canonical source order; a manifest is derived and its absence never invalidates a container. Materialized snapshot and manifest integrity uses the derived payload hash defined in this section. No separate canonical hash domain is created for materialized snapshots or manifests: MembersDigest is canonical and covers RevisionSet members, while a manifest is a derived member listing for acceleration only. ManifestHash and SnapshotHash are therefore not introduced.

Wire design: diff cache identity (Review)

A diff cache entry binds source revision, target revision, algorithm, algorithm version, payload hash, and payload or payload reference.

Use requires matching source, target, algorithm, version, and payload integrity; any mismatch means ignore and recompute. Reverse diffs are optional second entries.

Wire design: compression placement (Review)

ContentHash is computed over raw logical content bytes, never over compressed bytes, consistent with Section 19. No compression algorithm or registry value is frozen here.

Wire design: error and GC boundaries (Review)

Missing canonical objects, unsupported mandatory versions, unknown mandatory canonical records, and malformed canonical bytes are deterministic failures that MUST be reported distinctly (Section 38). Missing, invalid, or unknown-version derived data is never a canonical failure. Unavailable hash implementations, and containers declaring the None working mode, produce verification unavailable, which is never a canonical failure.

Unreachable is not invalid: unreachable objects are valid but reclaimable only under retention and reachability roots; no exact GC algorithm is frozen here.

Wire design: integrity coverage table (Review)

ContentHash covers the raw logical content bytes before any transformation. RecordHash covers a single canonical record encoding. MembersDigest covers the canonically encoded RevisionSet members. ContainerIntegrityHash covers the canonical container envelope and the canonical records only; derived units MUST NOT contribute to it, so canonical identity never depends on the presence, absence, or version of derived acceleration data (Sections 19 and 44).

All four domains are algorithm-selected metadata: each digest is computed with the container's declared hash working mode, and where that mode is None the domain carries no digest and verification is reported as unavailable. No domain is part of canonical semantic identity, and no domain makes a canonical container unreadable (Sections 10 and 19). ObjectHash, SnapshotHash, and ManifestHash are not introduced: object identity reuses optional ContentHash metadata, and derived unit integrity uses the derived payload hash defined in this section.

Wire design: deterministic encoding contract (Review)

Any canonical structure proposed for freezing MUST define field order, integer and length encoding, string encoding, collection ordering, duplicate rules, and hash input bytes.

Same semantic object yields identical canonical bytes and identical canonical hashes. Dictionary iteration order, memory addresses, filesystem order, wall clocks, locale, and platform behavior MUST NOT affect canonical bytes. Per-structure encodings remain TBD and nothing here is frozen.

Resolution: canonical object identity (Review)

Canonical object identity is the canonical reference together with the object it names, resolved through mandatory framing (this section). ContentHash is optional identity, lookup, and integrity metadata rather than the identity itself. Exact size is validation metadata: stored bytes whose raw length differs from the declared size are a deterministic integrity mismatch, but size is not part of canonical object identity. No ObjectHash domain is introduced, and physical offsets MUST NOT be used as identity.

Resolution: derived unit envelope separation (Review)

Identity, validity, provenance, version, and payload integrity MUST remain separate concerns. Identity is the addressing tuple of structure type, schema version, algorithm identity, algorithm version, source canonical identity, and creation generation; provenance is the source canonical identity; version is the schema and algorithm version; payload integrity is a separate derived payload hash over the deterministic payload encoding of that unit. Collapsing these into one hash is prohibited unless a rationale is stated and frozen. Field encoding remains TBD.

Resolution: diff identity (Review)

Diff identity is the tuple of source revision, target revision, algorithm identity, and algorithm version. Payload integrity is separate: the payload hash covers the deterministic payload encoding, and a mismatch means the unit is ignored and recomputed. Identity excludes the payload hash because two entries with identical endpoints and algorithm describe the same derived artifact and must deduplicate to one unit. Because identity is a deterministic function of endpoints plus algorithm identity and version, two different payloads under one identity are not an identity collision: they indicate corruption or an algorithm-version mismatch, and the unit MUST be ignored and recomputed.

Resolution: index rebuild (Review)

An index rebuild is a full deterministic pass over canonical records in canonical order, so identical canonical input with identical algorithm and version yields a functionally equivalent index. Byte identity across implementations is not required by Section 44. Key encoding, value encoding, ordering, checksums, and index versions remain TBD.

Resolution: physical layout and compression (Review)

Only logical ordering required for parsing, deterministic hashing, integrity, and recovery is protocol level. Alignment, padding, block size, packing, offsets, and compression block placement are implementation detail and MUST NOT be treated as identity. Compression is a storage representation applied above identity: ContentHash is computed over raw logical content bytes before any compression, transformation, or encryption, consistent with Sections 19 and 35. Compressing or transforming a derived unit does not affect canonical identity.

Resolution: version hierarchy (Review)

Protocol version governs semantic rules and is mandatory: an unsupported mandatory protocol version is a version error. Container version governs envelope interpretation and is mandatory. Derived versions govern acceleration only and are optional: unknown derived versions are ignored and recomputed. A separate schema-version axis MUST NOT be introduced unless it has its own registry entry in the existing registries; absent that entry, container version covers record layout. Protocol, container, and derived versions are independent and MUST NOT be collapsed into one value.

Resolution: round trip and test vectors (Review)

Canonical structures MUST satisfy round trip: decode followed by re-encode reproduces the original canonical bytes, and decoded semantics equal the original semantics. Derived units MUST satisfy derive, validate, and rebuild with functional equivalence to a fresh derivation. Required vector classes are empty, single member, multiple members, duplicate member, binary content, Unicode string, nested reference, reused object, missing derived, unknown derived version, invalid derived, and corrupt canonical object. No expected hash fixture is frozen until an executable canonical encoder produces it, so vectors remain Implementation Pending.

11 · VSN Mode

VSN Mode: Modern and Enterprise Normative — Semantics Frozen, Descriptor Encoding Pending

VSN Mode is the representation mode selected for a VSN container. There are exactly two modes, and they relate a user-facing mode name to an architectural representation name:

ModeRepresentationResource architecture
MODERNVertical Representationuses the Computation Unit for content representation and reconstruction
ENTERPRISEHorizontal Representationuses pre-materialized content; does not consume the Computation Unit for content reconstruction

Modern Mode is the Vertical Representation; Enterprise Mode is the Horizontal Representation. No third mode exists. A mode is not a product, not a subscription tier, not a profile, and not a separate library: there is one VSN library, one common semantic layer, and one canonical semantic model. The modes differ only in resource-consumption architecture — computation versus space.

Feature-parity invariant. VSN Mode MUST NOT remove, disable, or redefine any VSN library feature. Both MODERN and ENTERPRISE MUST expose the complete VSN library feature set: create and open a container, read, write, edit files, create revisions, inspect revision history, navigate revision relationships, resolve file heads, resolve content, recover and restore files, delete semantics, metadata operations, verification when available, and every other defined library operation. Mode selection MUST NOT change canonical revision records, revision identity, RevisionSet membership, FileHead semantics, or logical commit outcomes (Sections 12, 13, 14, 25).

Mode is not semantic identity. A VSN Mode MUST NOT become part of canonical object identity. Changing mode MUST NOT create a different semantic identity for the same logical content merely because the representation strategy changed. Semantic identity, representation mode, storage representation, verification metadata, and acceleration metadata are five separate concerns and MUST NOT be conflated. The mode in force is representation metadata, not content identity.

The mode in force for a container, and the representation identity and version of any Vertical representation a reader must reconstruct, MUST be determinable from canonical container data alone — without any derived structure and without executing any cryptographic hash algorithm (Section 10). The declaration site and encoding of that information are freeze blockers (Section 53).

Computation Unit (Normative — Review)

The Computation Unit is the logical component of a conforming implementation that performs permitted content representation, materialization, and reconstruction work. It covers: analysis of logical content for storage-efficient representation, deduplication, delta/diff and patch generation, content sharing decisions, chunking, compression transform application, and algorithmic reconstruction of logical content from a Vertical Representation.

Scope precision. No mode is claimed to perform literally zero operations; every software operation requires execution. The normative distinction is narrower and exact: MODERN Mode uses the Computation Unit for content representation and content reconstruction, while ENTERPRISE Mode MUST NOT consume the Computation Unit for content reconstruction, because its content is already pre-materialized. Ordinary work that is not content representation reconstruction — reading bytes, copying bytes, parsing container metadata, enumerating records, resolving references, validating lengths and extents, and ordinary I/O — is not Computation Unit reconstruction work and MUST NOT be described as such.

Enterprise Mode (Horizontal Representation) — Normative — Review

Central rule. Enterprise Mode is the compatibility-oriented mode that minimizes reconstruction requirements by storing pre-rendered, pre-materialized content. For file editing through the VSN library, a Horizontal Representation MUST persist the resulting logical file content as a FULL COPY. The edit operation MUST NOT introduce a content reconstruction instruction chain.

enterprise / horizontal: edit and recovery
edit:
previous file state -> EDIT -> resulting logical content -> FULL COPY -> persist

recovery:
VSN storage -> pre-materialized content -> COPY / MATERIALIZE -> logical file

No content reconstruction dependency. A Horizontal edit MUST NOT depend on diff computation, delta reconstruction, patch application, deduplication reconstruction, algorithmic content synthesis, previous-revision reconstruction, content reconstruction instructions, a storage-optimization engine, or a proprietary optimization algorithm in order to obtain the resulting file content. The resulting logical content MUST be directly represented by the stored pre-materialized content representation.

Pre-Materialized Content (Normative — Review)

Pre-Materialized Content is the normative term for content stored in a Horizontal Representation whose complete logical content, required for the corresponding revision and file state, is already present in the VSN representation. Recovery of that state is a copy or materialization of stored bytes and consumes no Computation Unit reconstruction work.

Pre-Materialized Content is canonical persisted content. It MUST NOT be classified as a cache, a checkpoint, a derived artifact, an optional optimization, or a materialized snapshot (Section 10). Because it is required for Enterprise Mode recovery, deleting it is deleting canonical recovery data and MUST be reported as a missing object or integrity failure under Section 38, never as a harmless cache eviction. The increased storage consumption is an intentional architectural trade-off, not waste. Enterprise Mode MAY share one pre-materialized object between revisions whose complete logical content is identical, because sharing complete content introduces no reconstruction dependency; it MUST NOT store a partial content object whose completeness depends on other stored data. Enterprise recovery MUST work without SHA-256, BLAKE3-256, or any other cryptographic hash algorithm (Sections 10 and 19), and compression and encryption remain orthogonal physical transforms of the stored bytes (Sections 34 and 35).

Modern Mode (Vertical Representation) — Normative — Review

Central rule. Modern Mode is the storage-efficient, computation-oriented mode. It uses the Computation Unit to reduce storage consumption and performs permitted content representation and reconstruction work. The Computation Unit is an intentional and normative part of the architecture, not an implementation detail: a reader that supports a declared Vertical Representation MUST invoke the Computation Unit to reconstruct the logical content from that representation and the canonical source data it names.

modern / vertical: edit and recovery
edit:
logical content -> COMPUTATION UNIT (analyze, transform, deduplicate,
                     generate representation, produce reconstruction data)
                -> compact representation -> VSN revision

recovery:
VSN representation -> COMPUTATION UNIT (reconstruct) -> logical content

Permitted techniques. Modern Mode MAY use deduplication, content sharing, delta/diff representation, patch representation, compressed or shared representations, chunking, revision-to-revision reuse, indexing, caching, algorithmic reconstruction, other supported storage-efficient algorithms, and future representation algorithms. No single optimization algorithm is mandated. This specification defines the required semantics and recovery properties, not one implementation algorithm, and MUST NOT require one specific algorithm.

Permitted is not unspecified. Future or implementation-specific Vertical methods are permitted only when the representation provides sufficient information and normative semantics for deterministic recovery by an implementation that supports it. Every Vertical Representation MUST carry a representation identity and representation version so a reader can decide before attempting reconstruction whether it supports that representation; an unsupported representation MUST be reported as an unsupported transform and never as corrupt data (Section 38). Representation identity and version values are registry-backed and unallocated (Section 46); their encoding is a freeze blocker (Section 53).

Language discipline. Modern Mode may reduce storage consumption and may require additional computation. This specification MUST NOT state that Modern Mode always produces smaller VSN files, and MUST NOT present either mode as better or worse; the two are an architectural resource choice with different storage and computation characteristics and no measured benchmark data exists (Section 43).

Vertical computation contract (Normative — Review)

This contract defines the interface of the Computation Unit work, not one optimization algorithm. A Vertical Representation MUST carry, or canonically reference, the information needed to answer every question below deterministically. Field encoding is a freeze blocker (Section 53); no encoding is frozen here.

  1. Source identification — which canonical content objects supply the source data, named by hash-independent canonical reference, never by physical offset.
  2. Destination identification — which reconstructed logical content object the computation produces.
  3. Required computation data — instructions, operands, chunk maps, or delta data needed to perform the computation.
  4. Computation order — how dependent steps are ordered, explicitly declared rather than implied by container layout.
  5. Dependency expression — how referenced source content is declared.
  6. Algorithm selection — how a reader knows which representation algorithm to invoke: representation identity plus representation version, registry-backed (Section 46).
  7. Unsupported algorithm — an unsupported representation identity or version is reported as an unsupported transform, never as corruption, and never as a reason to invalidate the container (Section 38).
  8. Canonical residue — what remains canonical if the optional optimization algorithm is unavailable: all data the representation itself requires. It MUST NOT silently reduce to derived data.
  9. Re-materialization — an optimized representation MAY be replaced or re-materialized, including by an Enterprise full-copy representation, without changing semantic meaning or semantic identity.
  10. Classification — which parts are canonical and which are derived or optimization metadata: data required to reconstruct canonical content is canonical for that representation; indexes, caches, optional hashes, lookup tables, and acceleration manifests remain derived.
  • Data, instructions, operands, and referenced source content that a selected Vertical Representation requires are canonical recovery data for that representation. Deleting such a component MUST be treated as deleting canonical recovery data, never as deleting a harmless cache, and the canonical/derived classification rule of Section 10 applies.
  • A Vertical Representation MUST NOT depend on derived acceleration data — indexes, manifests, checkpoints, materialized snapshots, or diff caches — for recovery (Section 10). It MAY depend only on canonical data named by its own representation.
  • Reconstruction MUST be deterministic and MUST NOT require a cryptographic hash algorithm, unless the representation explicitly declares a digest as part of its own representation contract. Such a declared digest is metadata of that representation and MUST NOT become the canonical identity of content (Sections 10 and 19). Hash working mode remains independent of VSN Mode: Modern plus None, BLAKE3-256, or SHA-256, and Enterprise plus each of those modes, are all valid combinations.
  • Representation durability. A representation required for canonical recovery MUST either be part of the mandatory supported representation set, or have an in-container representation satisfying the archival recovery requirements. A valid canonical container MUST NOT depend solely on an optional acceleration algorithm that future readers are not required to understand. Verification availability remains separate from recoverability (Section 10).

Relation to object identity. A cryptographic hash, a physical offset, an index entry, and a diff algorithm MUST NOT be used as content identity in either mode (Section 10).

Framing is mode-independent (Normative — Frozen)

Record framing MUST be identical regardless of VSN Mode. Mode MUST NOT change record framing, record discovery, record type semantics, field interpretation, canonical identity, or accepted-state rules. This is required for interoperability and is the reason the two modes are operating modes of one format rather than separate formats.

Physical re-layout. Changing physical object layout MUST NOT change semantic meaning. Physical ordering, offsets, padding, block boundaries, packing, compression placement, and index layout MUST NOT affect canonical semantics, and object identity and reference resolution MUST survive all such re-layout.

Neither mode is better or worse; no numerical claim is made anywhere in this specification, because no measured benchmark data exists. Compatibility positioning follows from the resource model rather than replacing it: Enterprise minimizes the number of content reconstruction mechanisms required for recovery and is therefore compatibility-oriented, while Modern is modern, storage-efficient, and representation-flexible. This specification MUST NOT claim that Enterprise will be readable by every future implementation, and MUST NOT imply that Modern is less compatible by definition — compatibility depends on whether the representation used falls within the mandatory supported specification, together with versioning, mandatory framing, mandatory record semantics, mandatory baseline representations, supported codecs, and defined recovery rules (Sections 6, 7, 34).

No Mode-specific canonical byte decision remains open, and the two-mode architecture resolves no freeze blocker listed in Section 53 beyond what Sections 10 and 53 already record.

12 · Revision Model

Revision Model Normative — Frozen

A Revision is an immutable historical state of a logical file at a point in time. A Revision is canonical. It is not the derived materialized snapshot defined in Section 10; the two concepts use different names and MUST NOT be conflated. A Revision names its content through a ContentRef; how that content is persisted and represented depends on VSN Mode (Section 11), which NEVER changes revision identity, revision relationships, or the logical content the revision denotes. A revision record is identical in both modes except for the representation its ContentRef names.

  • Revisions are immutable once created; they cannot be modified.
  • Each Revision belongs to exactly one FileId, which is the authoritative identity of the logical file.
  • Restore operations select a Revision by its RevisionId within a FileId's scope. “VSN” names the container format only; it is never a revision selector, and this specification uses no undefined revision-selector term.
  • FileId is authoritative over pathname: identity is never inferred from path or content.

13 · RevisionSet

RevisionSet Normative — Frozen

A RevisionSet groups one or more Revisions for review and acceptance.

  • State machine: DRAFT → PENDING_REVIEW → ACCEPTED or REVISION_REQUIRED.
  • RevisionSet state is orthogonal to crash recovery and physical write state.
  • No SEALED state exists in the protocol.
  • No RECOVERY_REQUIRED state exists for RevisionSet (that applies only to ApplyTransaction).

14 · FileHead

FileHead Normative — Frozen

A FileHead records one authoritative head RevisionId per logical file and provides conflict detection for atomic updates. “VSN” in this section means the container format, never a revision selector.

  • head RevisionId: the single authoritative pointer to the currently accepted Revision for this FileId. FileHead MUST NOT carry a second competing head reference.
  • ExpectedRevisionId (protocol-level precondition, not canonical stored state): the RevisionId a client expects to commit against.
  • If the actual head RevisionId does not match ExpectedRevisionId, return CONFLICT_STALE_EXPECTED.
  • FileHead updates are atomic: either fully applied or not applied at all.
  • Stale-accept conflict: if a RevisionSet is accepted but FileHead is stale, the accept is rejected.

15 · Logical Commit vs Physical Projection

Logical Commit vs Physical Projection Normative — Frozen

A Logical Commit is the protocol-level acceptance event that makes state durable.

A Physical Projection is the materialization of accepted state to workspace files.

  • Core invariant: After a Logical Commit, the canonical state is durable and recoverable.
  • Physical Projection MAY be deferred, skipped, or retried without affecting logical state.
  • Crash recovery operates on logical state, not physical files.
  • Logical Commit and Physical Projection are explicitly distinct operations.

16 · ApplyTransaction

ApplyTransaction Normative — Frozen

An ApplyTransaction is a physical write operation that materializes accepted state.

  • Physical-state state machine: PENDING → APPLYING → APPLIED or ROLLED_BACK.
  • ApplyTransaction is separate from RevisionSet state.
  • If crash occurs during APPLYING, physical state becomes RECOVERY_REQUIRED.
  • RevisionSet state does NOT include RECOVERY_REQUIRED; that is a physical-state concern only.

17 · Crash Recovery

Crash Recovery Normative — Frozen

Crash recovery is marker-based: recovery decisions are driven by explicit markers in durable state. The full normative model, including the accepted-state authority rule, the transaction state model, every torn-write boundary, prefix recovery, the recovery algorithm, and the failure taxonomy, is frozen in Section 10 as rules RC-01 to RC-45 with vectors T1 to T32.

  • If a valid CommitMarker covering a complete and semantically valid record set is present at the highest Generation, that commit is the accepted state; everything after it is an uncommitted tail (RC-01, RC-13).
  • If no valid marker covers a complete set, the transaction is rolled back and the previous effective commit, if any, stands (RC-05, RC-19).
  • No heuristic recovery: never infer commit status from timestamps, file sizes, record order, highest identifier, or partial writes (RC-41).
  • Recovery operates on logical state, not physical file content, and never requires an index, cache, or checkpoint (RC-22).

19 · Integrity

Integrity Normative — Frozen

BRP preserves four distinct integrity domains. They MUST NOT be conflated. Coverage — not algorithm — defines each domain, and each domain covers exactly the bytes stated below.

  • ContentHash: digest of the raw logical content bytes before any transformation, compression, or encryption.
  • RecordHash: digest of a single canonical record encoding.
  • MembersDigest: digest of the canonically encoded RevisionSet members.
  • ContainerIntegrityHash: digest of the canonical container envelope and the canonical records only. Derived acceleration units are outside its coverage and MUST NOT contribute to it, so an implementation with acceleration data and an implementation without it compute the same ContainerIntegrityHash.

All four domains are algorithm-selected metadata: each digest is computed with the container's declared hash working mode (None, BLAKE3-256, or SHA-256). Where the declared working mode is None, the domain carries no digest and verification for that domain is reported as unavailable. No integrity domain is part of canonical semantic identity.

Canonical decoding and recovery MUST NOT require any of these digests to be recomputed, and a digest mismatch MUST NOT be reported as malformed or undecodable canonical data.

22 · Diff

Diff Normative — Frozen

A diff computes the difference between two revisions and MAY produce a DiffArtifact. No particular diff algorithm is mandatory for canonical semantics: revision relationships are canonical, diff algorithms are optional derived mechanisms, and no derived diff cache is ever required for recovery. In Enterprise Mode, content is pre-materialized and independently recoverable without any diff. In Modern Mode, content MAY be stored as a canonical delta-style representation that declares the source content it needs; that data is canonical recovery data (Section 11) and is not a derived diff cache. Neither mode's canonical semantics depend on any diff algorithm being available.

A stored DiffArtifact is derived acceleration data (see Section 10): it is not canonical semantic state. An implementation MAY omit a diff cache and MAY store forward or reverse diffs. A cached diff MUST be checked against source and target revision identity before use. Unknown or invalid cached diffs MUST be ignored and recomputed. Canonical equality does not depend on whether a diff cache exists, and a derived diff cache MUST NOT be the only representation from which canonical content can be reconstructed.

34 · Compression

Compression Normative — Review

Compression is a storage and transport representation, never part of semantic identity. The mandatory baseline archival representation is NONE: every conforming reader MUST be able to read the uncompressed canonical representation without any optional codec present.

Compression is orthogonal to VSN Mode (Section 11): pre-materialized content in a Horizontal Representation MAY itself be stored compressed as a physical transform of complete logical content, and the source data declared by a Vertical Representation MAY be compressed. In both modes the NONE baseline of this section continues to apply, and compression never converts a stored representation into a content reconstruction instruction dependency nor changes a mode's recovery requirements.

ContentHash, where present, refers to the raw logical content bytes before compression or any other physical transformation. Compressed representation is optional profile material; standardized algorithms such as Zstandard MAY be defined by an optional profile. An implementation without the corresponding optional codec MUST be able to determine that the transform is unsupported and report it as an unsupported transform; it MUST NOT treat the semantic data as cryptographically corrupt or as malformed canonical data.

35 · Encryption and Security Profiles

Encryption and Security Profiles Normative — Review

Encryption is an optional security profile applied after canonical content identity is established. Two concerns MUST be kept separate: semantic identity independence from ciphertext, and plaintext recoverability.

  • Semantic identity independence: encryption MUST NOT change canonical semantic identity or the canonical bytes of the identity-bearing structures. Ciphertext is a physical representation, not an identity.
  • Plaintext recoverability: recovering plaintext MAY require the required key and the required decryption mechanism. This specification does not promise keyless plaintext recovery.
  • An unavailable or incorrect encryption key MUST be reported as an access or decryption failure. It MUST NOT be reported as an integrity mismatch, as a hash failure, or as malformed canonical data.
  • An implementation without the required decryption mechanism MUST report an unsupported transform, not corruption.

38 · Error Model

Error Model Normative — Frozen

Turn the current error table into a normative error registry.

A canonical reference that names a stored object which has no corresponding stored bytes is a deterministic reference failure. Stored bytes that do not match their expected digest are a deterministic integrity mismatch. An invalid derived unit MUST NOT invalidate a canonically valid container: it MUST be ignored and recomputed. An unknown derived version MUST NOT invalidate a canonically valid container: it MUST be ignored and recomputed.

The following states are distinct and MUST NOT be conflated. In particular, hash algorithm unavailable is not canonical data corrupt.

  • malformed or decode failure — the canonical bytes violate mandatory canonical decoding rules.
  • missing object — a canonical reference resolves to no stored bytes.
  • unsupported transform — a compression or encryption transform cannot be applied or reversed by this implementation.
  • verification unavailable — no digest could be computed or compared, because the required hash working mode or implementation is unavailable, or because the declared working mode is None. This is not a failure of the canonical data.
  • integrity mismatch — a digest was computed and compared and did not match.
  • unknown mandatory canonical record — a record type that a conforming reader is required to understand was not recognized.
  • unsupported mandatory version — a declared mandatory protocol or container version is not supported.
  • access or decryption failure — the required key or decryption rights are unavailable or incorrect (Section 35).

A reader MUST be able to report verification unavailable while still returning successfully decoded and recovered canonical data. Error identifiers apply only where this specification defines a naming convention; no error encoding is invented here.

39 · Error Wire Format

Error Wire Format Normative — Frozen

Error identifiers and their semantics are frozen in Section 10 as the error registry table with rules VR-28 and VR-29. An error identifier is a u16be diagnostic value drawn from the core range 0x0000–0x7FFF, with 0x8000–0xFFFE reserved for vendor diagnostics.

Error identifiers are diagnostic semantics, not canonical data: they are never part of canonical state, never hashed, and never affect identity, membership, parentage, accepted state, or logical content (VR-29). Once published, an error identifier's meaning is immutable and the identifier is never reused (VR-28). Errors are returned to a caller rather than embedded as canonical records, so no failure value appears on the container wire.

44 · Interoperability

Interoperability Normative — Frozen

If two independent implementations support the same BRP protocol version, VSN format version, RCMP encoding version, and required capabilities, a .vsn produced by one implementation MUST be readable and semantically equivalent when opened by the other.

Interoperability equivalence is judged on canonical data and canonical semantics only, not on the presence, absence, or version of derived acceleration data. An implementation with derived data and an implementation with canonical data only MUST produce semantically equivalent results from the same canonical state. Unknown or divergent derived versions MUST NOT break canonical equivalence where fallback to canonical reconstruction is possible.

The selected hash working mode (None, BLAKE3-256, or SHA-256) MUST NOT be part of interoperability equivalence and MUST NOT be a readability requirement. Two implementations that declare different working modes MUST still be able to decode and recover the same canonical semantic state from the same canonical bytes; only reported verification status may differ.

VSN Mode (Section 11) is likewise not part of semantic identity or interoperability equivalence. Record framing, record discovery, record type semantics, and field interpretation MUST be identical in both modes. A reader MUST recover the same logical content bytes from an ENTERPRISE pre-materialized representation and from a MODERN representation of the same canonical content state, provided it supports the declared representation identity and version. An unsupported representation identity or version is reported as an unsupported transform (Section 38) and is not corruption. Physical representations of the two modes need not be byte-identical, and physical-byte equality is not required; only the recovered semantic state and logical content are.

The representation of Modern Mode. Content MAY be stored under any supported storage-efficient representation (delta, patch, deduplicated, shared, chunked, algorithmic, or future), provided canonical recovery is deterministic.

The representation of Enterprise Mode, in which every persisted edited file state is stored as a full copy of its complete logical content.

Flexible Representation
A Vertical Representation chosen by the implementation. Canonical recovery data for the content it represents, not a cache.
Reconstruction
Deterministic derivation of logical content from a representation plus the canonical source data it names. Performed by the Computation Unit in Modern Mode; not required for edited content in Enterprise Mode.

Persistent canonical identifier of one canonical content object within one VSN container. Hash-independent, physical-location-independent, and never reused within the container lifetime (Section 10, ID-01 to ID-16). Required inside ContentRef.
ExpectedRevisionId
Client-supplied commit precondition naming the RevisionId it expects to be head. Operation precondition only, never canonical stored state and never a second head reference (Section 14, ID-42).
VSN
The container format name only (VSN-1), plus the .vsn file extension. Never a revision selector: revisions are selected by RevisionId.
