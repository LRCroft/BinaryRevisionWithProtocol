Core principle. BRP defines protocol semantics, canonical data representation, binary encoding rules, revision semantics, transactional semantics, integrity rules, compatibility rules, and conformance requirements. .vsn is a standardized self-contained container representation of BRP revision data — it is not the protocol itself. Libraries are implementations of BRP; applications consume BRP libraries. No implementation is authoritative over the specification.

01 · Scope

Scope Normative — Frozen

BinaryRevisionWithProtocol (BRP) is an open, language-independent, platform-independent, implementation-independent protocol for immutable file revisions, transactional multi-file changes, diff, restore, and crash-safe workspace projection — without requiring Git.

BRP covers the same ground as the previous Documentation page (revision model, FileId identity, RevisionSet lifecycle, content addressing, restore scopes, recovery) and adds the normative wire format: BRP Canonical Model, RCMP-1 canonical encoding, VSN-1 self-contained container, and BRP Conformance.

The protocol MUST NOT depend on Git, Git object format, a particular database, filesystem, operating system, programming language, serialization library, server, or cloud provider. The specification itself is the authority.

02 · Normative Language

Normative Language Normative — Frozen

Normative requirements use RFC-style interpretation. MUST, MUST NOT, REQUIRED, SHALL, and SHALL NOT state absolute conformance rules. SHOULD and SHOULD NOT state strong recommendations with documented exceptions. MAY and OPTIONAL mark truly optional behavior.

Separate Normative (conformance rules) from Informative (explanation and examples), Implementation-defined (documented local choices), Implementation-specific (non-interoperable internals), and Experimental (not for production claims). An implementation-defined behavior MUST NOT change protocol interoperability.

03 · Terminology

Terminology Normative — Frozen

BRP is the protocol identifier. BRP Protocol is the semantic ruleset. BRP Canonical Model is the shared data model. RCMP-1 is the canonical encoding. VSN-1 is the self-contained container format. BRP Conformance is the measurable test suite. A Revision is one immutable state of one logical file. A RevisionSet is a reviewable multi-file transaction. FileHead points at the accepted revision. ContentRef carries content identity and size. DiffArtifact is derived and disposable. ApplyTransaction is the physical projection and recovery transaction. Logical Commit is acceptance of a reviewed RevisionSet. Workspace Projection materializes accepted state as ordinary files.

07 · Compatibility Model

Compatibility Model Normative — Frozen

.vsn is a companion sidecar file that travels with its logical file and carries its revision state/history and the information required to reconstruct or locate those revisions.

Normative terms in this page follow RFC 2119: MUST / MUST NOT are absolute requirements, SHOULD / SHOULD NOT are strong recommendations with documented exceptions, and MAY marks truly optional behavior.

file-local sidecars
project/
`-- src/
    |-- Program.cs
    |-- Program.cs.vsn
    |-- UserService.cs
    `-- UserService.cs.vsn
  • One logical file maps to one sidecar: Program.cs + Program.cs.vsn.
  • The sidecar carries FileId, revision history, revision metadata, accepted/head information, revision references, and references to content/revision data.
  • A valid sidecar MUST embed every byte required to reconstruct each retained Revision. External storage MAY exist for sync, cache, backup, or collaboration, but it MUST NOT be required for retained-revision reconstruction.
  • FileId is authoritative identity. Filename is not identity.
  • Rename preserves FileId; move preserves FileId.
  • The .vsn file is not the protocol itself. It is one representation/storage mechanism for the protocol; other backends can exist.
  • Design goal: copy both files to another workspace and the revision history travels with them.

14 · Canonical Serialization

Canonical Serialization Normative — Frozen

Every semantic object in BRP MUST have a single canonical RCMP-1 byte representation. The same semantic object MUST produce identical RCMP-1 bytes and identical SHA-256 digests across all conforming implementations. Canonicalization rules: deterministic field ordering, minimal integer width, map key ordering (numeric keys by value, string keys by UTF-8 byte order), no optional fields with default values in canonical form, no padding. Non-canonical encodings MUST be rejected or normalized on decode; they MUST NOT produce different semantic interpretations.

15 · RCMP-1

RCMP-1 Normative — Review

RCMP-1 is the canonical binary encoding for BRP. It defines deterministic encoding for all core types. No RCMP-1 encoder, schema, or byte-level test vector exists in this repository; this section remains Normative — Review and wire patterns below are UNFROZEN / NOT PART OF V1 until conformance vectors are published.

TypeEncoding Rule (summary)
Unsigned IntegerMinimal-width varint (LEB128-style), canonical width only
Signed IntegerZigZag + varint, canonical width only
BooleanSingle byte: 0x00 = false, 0x01 = true
NullSingle byte: 0xC0
UTF-8 StringLength-prefixed (varint) + raw UTF-8 bytes
Byte StringLength-prefixed (varint) + raw bytes
UUIDExactly 16 bytes, big-endian (RFC 4122 network order)
SHA-256Exactly 32 raw bytes
TimestampSigned 64-bit LE, Unix epoch nanoseconds UTC
ArrayLength-prefixed (varint) + concatenated elements
MapLength-prefixed (varint) + key/value pairs sorted by key (numeric keys by value, string keys by UTF-8 byte order); duplicate keys rejected
RecordTag byte + length + fields in schema order
ExtensionTag 0xF0-0xFF reserved; ExtensionId (varint) + Version (varint) + Flags (varint) + Length (varint) + Payload

Byte order for multi-byte integers: little-endian unless explicitly noted (UUID, SHA-256 are big-endian). Canonical integer width: minimal varint encoding only; no padding bytes permitted. Maps MUST use deterministic key ordering as specified. Duplicate map keys MUST cause decode failure. Floating-point values are excluded from core records; if needed, use integer scaled representation or extension.

16 · VSN-1 Container Format

VSN-1 Container Format Normative — Review

VSN-1 is the self-contained container format for BRP revision data. A valid VSN-1 container MUST allow full reconstruction of all retained revisions without external dependencies.

container structure
VSN-1
|-- Magic: 0x56 0x53 0x4E 0x31 ("VSN1")
|-- Format Version: uint8 (1)
|-- Flags: uint8
|-- Protocol Identity: ProtocolVersion, ContainerFormatVersion, RecordVersion, EncodingVersion
|-- File Identity: FileId (UUID), CurrentPath
|-- Revision Records: array of Revision records (RCMP-1 encoded)
|-- Content Records: array of Content records (raw bytes + ContentRef)
|-- Index: RevisionId -> offset, ContentRef -> offset
|-- Integrity Records: ContainerIntegrityHash (SHA-256 of all preceding data)
|-- Extension Area: optional extensions
|-- Commit Marker: Generation (uint64), CommitTimestamp, IntegrityHash
  • Magic bytes: 0x56 0x53 0x4E 0x31 ("VSN1" in ASCII)
  • Format version: single byte, current value 0x01
  • A reader MUST reject a container whose format version it does not support
  • All multi-byte integers in container header: little-endian
  • ContentRef carries content identity (SHA-256 of raw bytes plus exact size)
  • Same content MUST yield the same content identity; every retained Revision MUST stay independently reconstructable
  • Commit marker with generation counter enables atomic write detection

17 · Binary Record Format

Binary Record Format Normative — Review

Each record in the VSN-1 container follows a common binary framing:

FieldTypeDescription
Taguint8Record type identifier (0x01-0xEF for core, 0xF0-0xFF for extensions)
LengthvarintPayload length in bytes
PayloadbytesRCMP-1 encoded record data

Core record tags (normative):

TagRecordDescription
0x01ProtocolIdentityProtocol version, container format version, encoding version
0x02FileIdentityFileId (UUID), current path snapshot
0x03RevisionRevisionId, FileId, ParentRevisionId, RevisionSetId, ContentRef, PathSnapshot, Presence, Metadata, CreatedAt, Actor
0x04ContentContentRef, raw bytes (or reference to external storage)
0x05RevisionSetRevisionSetId, state, members, MembersDigest, CreatedAt, Actor
0x06FileHeadFileId -> HeadRevisionId mapping
0x07IndexRevisionId/ContentRef -> offset mappings
0x08IntegrityContainerIntegrityHash, per-record checksums
0x09CommitMarkerGeneration, timestamp, integrity hash
0xF0-0xFFExtensionExtensionId + Version + Flags + Length + Payload

Records MUST appear in dependency order. Unknown core tags (0x01-0xEF) MUST cause decode failure. Unknown extension tags (0xF0-0xFF) follow extension rules (section 35).

18 · Framing

Framing Normative — Review

VSN-1 uses length-prefixed framing for all records. There is no delimiter-based framing.

  • Each record: Tag (1 byte) + Length (varint) + Payload (Length bytes)
  • Varint encoding: LEB128-style, minimal width, little-endian byte order
  • Maximum record payload size: 2 GiB (2^31 - 1 bytes)
  • Streaming readers MUST process records incrementally without loading entire container
  • No padding bytes between records. Records are tightly packed.
  • Container ends at CommitMarker record. Trailing bytes after CommitMarker MUST cause integrity failure.

19 · Integrity

Integrity Normative — Frozen

Integrity verification is mandatory at multiple levels:

  • ContainerIntegrityHash: SHA-256 of all bytes from start through last record before Integrity record. Verified on every container open.
  • Per-record checksums: CRC32C (Castagnoli) of payload in Index record for fast corruption detection.
  • Content integrity: Each Content record's raw bytes MUST match its ContentRef (SHA-256 + size). Verified on read.
  • CommitMarker integrity: Generation counter prevents rollback.
  • On integrity failure: reader MUST fail with CORRUPT_VSN or INTEGRITY_FAILURE. MUST NOT attempt silent repair.

20 · Hashing

Hashing Normative — Frozen

SHA-256 is the mandatory core hash algorithm for BRP.

ContextBinary FormText Form
ContentHash32 raw bytessha256:<64 lowercase hex>
RecordHash32 raw bytessha256:<64 lowercase hex>
MembersDigest32 raw bytessha256:<64 lowercase hex>
ContainerIntegrityHash32 raw bytessha256:<64 lowercase hex>
  • ContentHash = SHA-256(raw content bytes) - computed BEFORE compression, encryption, or container storage
  • RecordHash = SHA-256(canonical RCMP-1 encoding of record)
  • MembersDigest = SHA-256(canonical RCMP-1 array of RevisionSet members sorted by Ordinal)
  • ContainerIntegrityHash = SHA-256(all container bytes up to Integrity record)
  • These four hash contexts MUST NOT be conflated. Each has distinct semantic meaning.

08 · Data Model

Data Model Normative — Frozen

A Revision is one immutable state of one logical file. A committed Revision is never rewritten. Revisions remain addressable according to retention policy; old revisions may be purged only under documented GC rules. Restore creates new revision state based on an old revision; it never mutates the source revision. Workspace files are projections; FileHead represents accepted state.

11 · RevisionSet Model

RevisionSet Model Normative — Frozen

references
Revision
   |
   `-- ContentRef
          |
          `-- Content Object / Storage
  • ContentRef identifies raw logical bytes by SHA-256 and exact byte size.
  • Canonical form: sha256:<64 lowercase hexadecimal characters>.
  • ContentHash = SHA-256(raw bytes), computed before compression, encryption, or container storage transformation. Content identity MUST be independent of storage representation; LF, CRLF, BOM, invalid UTF-8, binary data, and zero-length content MUST remain distinct with no implicit text normalization.
  • Binary-safe: arbitrary bytes are first-class. No newline or encoding normalization.
  • LF and CRLF remain distinct byte sequences; BOM remains content; invalid UTF-8 is not silently replaced.
  • ContentRef is authoritative for identity; DiffArtifact is derived. Legal transitions: DRAFT → PENDING_REVIEW → ACCEPTING → ACCEPTED, plus PENDING_REVIEW → REJECTED, ACCEPTING → CONFLICTED, DRAFT → ABORTED. Every other transition is illegal, including any transition out of the terminal states.

RevisionSet is the logical change transaction. ApplyTransaction is the physical workspace projection and recovery transaction. Logical commit updates canonical accepted state (FileHeads, path index, WorkspaceVersion, LogicalCommitMarker, accept idempotency result). Physical projection finalization is separate cleanup.

22 · Library Capabilities

Library Capabilities Specification

Every BinaryRevisionWithProtocol library operates on the same protocol semantics and the same .vsn representation. Different language implementations may expose idiomatic APIs, but they must produce equivalent protocol behavior.

A conforming library must be able to operate on a self-contained .vsn file without requiring Git, a database, a server, or an external revision/content store for retained revisions.

Self-contained .vsn

The fundamental local model is Program.cs + Program.cs.vsn. The sidecar must contain all information and content required to reconstruct every retained Revision of its logical file.

self-contained sidecar
              Program.cs.vsn
                    |
      +-------------+-------------+
      |             |             |
  File Identity  Revisions     Content
      |             |             |
      +-------------+-------------+
                    |
               Library API
                    |
      +-------------+--------------+
      |             |              |
   History        Diff          Restore

A valid .vsn must not depend on Git, an external database, a remote revision server, or an external blob store for reconstruction of retained revisions.

Capability categories

1. Open / Create / Verify

Protocol-level capabilities equivalent to CreateVsn, OpenVsn, VerifyVsn: create a new sidecar, open an existing one, detect unsupported protocol versions, validate structure and required metadata, validate integrity, detect corruption, and safely reject malformed data.

2. File Identity

Capabilities equivalent to GetFileIdentity, GetFileId, GetCurrentPath: expose FileId and the current logical path. Identity is independent of filename and content hash, and preserved across rename (src/A.cs to src/B.cs keeps the same FileId) and move.

3. Revision Management

Capabilities equivalent to CreateRevision, GetRevision, GetRevisionContent, GetRevisionMetadata, VerifyRevision: create revisions, read content and metadata, verify integrity, and inspect parent revision, RevisionSet, actor, path, presence, change flags, and restore lineage. A committed Revision is immutable.

4. Revision History

Capabilities equivalent to GetRevisionHistory, GetRevisionById, GetLatestRevision, GetHead: navigate R1 -> R2 -> R3 -> R4 and inspect any retained revision without an external service.

5. RevisionSet Management

Capabilities equivalent to BeginRevisionSet, StageRevision, SealRevisionSet, GetRevisionSet, AcceptRevisionSet, RejectRevisionSet. A RevisionSet groups multiple file revisions into one logical change set; each member identifies a FileId with BaseRevisionId (expected prior state) and TargetRevisionId (proposed state); MembersDigest gives deterministic membership integrity; acceptance is all-or-nothing. Public states: DRAFT, PENDING_REVIEW, ACCEPTING, ACCEPTED, REJECTED, CONFLICTED, ABORTED. No SEALED state; no RECOVERY_REQUIRED here.

6. Diff

Capabilities equivalent to CompareRevisions, CreateDiff, GetDiff: compare two revisions for content equality, presence, path, metadata, binary and text content. DiffArtifact is derived, not canonical; restore must never require a pre-generated DiffArtifact.

7. Restore

Capability equivalent to RestoreRevision with scopes CONTENT_ONLY (bytes only), CONTENT_AND_PATH (bytes plus logical path), and FULL_STATE (bytes, path, and metadata). The library reads the source revision directly from the sidecar, never rewrites it, creates new state where the protocol requires it, fails when a scope cannot be fulfilled, and never depends on DiffArtifact.

8. File Operations

Create (first revision for a FileId), Modify (new revision parented on the previous one), Rename (path change, FileId preserved), Move (parent change, FileId preserved), Delete (ABSENT tombstone revision, history kept), Restore (new state from an existing revision). Never infer rename from matching content.

9. Integrity

Capabilities equivalent to VerifyContent, VerifyRevision, VerifyVsn, VerifyMembersDigest, VerifySerialization. SHA-256 content identity is sha256:<64 lowercase hexadecimal characters>. Invariant: every retained or addressable Revision must remain fully reconstructable byte-for-byte.

10. Transaction / Accept

Capabilities equivalent to AcceptRevisionSet and RejectRevisionSet. The library separates Logical Commit from Workspace Projection. Invariant: RevisionSet = ACCEPTED if and only if a Logical Commit exists. Acceptance updates canonical accepted state atomically and never reports success without a logical commit.

11. Crash Recovery

Capabilities equivalent to Recover, GetRecoveryState, VerifyProjection, Rollback, RollForward. ApplyTransaction owns physical recovery: LogicalCommitMarker absent means old accepted state plus projection rollback; present means new accepted state plus roll-forward. RECOVERY_REQUIRED belongs only to ApplyTransaction. Recovery never guesses from timestamps or current file contents.

12. Garbage Collection

Capabilities equivalent to GarbageCollect and Purge. Before deleting content, the library must establish it is no longer required by any retained or addressable revision or active protocol root, preserving: Retained Revision implies Reconstructable Content.

13. Serialization

Capabilities equivalent to Encode, Decode, CanonicalEncode, VerifyCanonicalEncoding: decode valid records, reject malformed ones, emit deterministic canonical bytes, validate UUIDs, timestamps, hashes, and extension maps, reject duplicate extension keys, and separate unknown optional from required extensions.

14. Conformance

Capabilities equivalent to RunConformanceTests and VerifyTestVector against shared semantic vectors: RCMP-1 bytes, content hashes, MembersDigest, revision and RevisionSet behavior, restore, recovery, idempotency, and path security. No library defines its own protocol interpretation.

Language API principle

The protocol defines semantics, not programming-language method names. For example, GetRevisionContent may surface as streams, byte iterators, readers, promises, or spans depending on the language. Those idiomatic mappings are not frozen here; language libraries will be designed after this contract is frozen.

Self-contained library requirement

A library MUST be able to open a valid .vsn and reconstruct every retained Revision using the .vsn itself, without requiring Git, a database, a server, or an external content store. The sidecar carries metadata, revision history, content, integrity, and protocol information sufficient for that file. External services may support sync, indexing, collaboration, or backup, but never reconstruction of retained revisions.

Future language libraries

Intended native implementations: C#, Python, Rust, JavaScript / TypeScript, Java, Go, C++. Each is Planned based on actual repository status — no library source exists yet, and no language API is frozen by this page.

25 · Workspace Projection

Workspace Projection Normative — Frozen

reconstruction path
RevisionId -> Revision -> ContentRef
  -> Embedded Content -> Raw bytes

Workspace Projection materializes the accepted state (FileHeads) as ordinary files in the workspace. The projection is a derived, read-only view of the canonical accepted state.

  • Projection applies all accepted RevisionSets in order, materializing each FileHead's ContentRef as a file at its PathSnapshot.
  • Projection is deterministic: same accepted state + same projection rules = same workspace files.
  • Projection MAY be incremental (only changed files) or full. Result MUST be identical.
  • External modifications to projected files are detected via EXTERNAL_MODIFICATION_DETECTED error on next operation.
  • Projection does not modify the .vsn container. It is a one-way materialization.

26 · Crash Recovery

Crash Recovery Normative — Frozen

Crash recovery applies to two distinct layers: VSN-1 container recovery (section 16) and ApplyTransaction workspace recovery.

ApplyTransaction Recovery: The logical commit marker determines the accepted state:

commit marker rule
LogicalCommitMarker absent
    -> accepted state remains old
    -> rollback projection

LogicalCommitMarker present
    -> accepted state is new
    -> roll forward projection
    -> finalize

RECOVERY_REQUIRED is a physical ApplyTransaction recovery state, not a RevisionSet state. It is not evidence that a RevisionSet was accepted or rejected.

VSN-1 Container Recovery: On open, reader checks CommitMarker generation. If generation matches previous valid generation, container is valid. If generation is incomplete (partial write detected), reader MUST surface CORRUPT_VSN or INCOMPLETE_WRITE — never silent corruption.

Recovery never guesses from timestamps, current file contents, or heuristics. Only the commit marker and generation counter are authoritative.

27 · Atomicity

Atomicity Normative — Review

The VSN-1 container MUST guarantee atomic writes. After an interrupted write, a reader MUST see either:

  • The previous valid committed generation, OR
  • A detected incomplete/corrupt state (surfacing CORRUPT_VSN or INCOMPLETE_WRITE)

It MUST NEVER silently expose partially committed metadata.

Mechanism: generation counter + commit marker + integrity hash. On write, new generation is written to a temporary location, integrity hash computed, then commit marker atomically updated (or file renamed). On read, generation counter and integrity hash are verified. If mismatch, previous generation is used.

This is separate from ApplyTransaction recovery (section 26), which protects workspace projection rather than the container itself.

UNFROZEN / NOT PART OF V1: Exact atomic write mechanism (append-only log, atomic rename, journal, generation counter) is not yet frozen. Implementations MUST document their mechanism.

28 · Concurrency

Concurrency Normative — Frozen

Protocol-level concurrency semantics without prescribing implementation mechanism:

  • Multiple readers MUST be safe concurrently.
  • A writer MUST NOT silently overwrite another writer's committed revision state.
  • Every mutation requiring an expected state MUST support an expected-state check: ExpectedHeadRevisionId, ExpectedWorkspaceVersion, or ExpectedGeneration.
  • A stale operation MUST result in CONFLICT error (or equivalent normative protocol error).
  • Locking mechanics (mutexes, database locks, OS locks, distributed locks) are implementation-defined. Implementations MUST document their mechanism without changing these guarantees.
  • Optimistic concurrency with expected-state checks is the normative model. Pessimistic locking is permitted but not required.

29 · Paths & Rename

Filesystem Paths and Rename Semantics Specification

Libraries MUST separate the logical protocol path in the sidecar from the host filesystem path. The sidecar MUST use protocol path rules on every OS. Rename and move mean: same FileId, new PathSnapshot, new Revision. Delete-A plus Create-B with identical bytes MUST NOT imply rename; rename needs authoritative identity, never hash, name, diff, timestamp, or timing similarity. OS separators, reserved names, case, Unicode, symlinks, junctions, mounts, and hard links MUST NOT change FileId semantics; absolute paths, .., and NUL stay rejected.

31 · Interop & Versions

Cross-Language Interoperability and Versioning Specification

A .vsn from one conforming implementation MUST be readable by another supporting the same protocol version and required capabilities. This is a conformance requirement; no cross-language implementations exist in this repository yet.
