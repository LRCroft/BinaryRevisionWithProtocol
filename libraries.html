01

Introduction

This page is the implementation and API capability reference for the VSN Library. It describes what an implementation may do with a .vsn file and how each operation relates to the frozen VSN-1 architecture.

This page is documentation of a Library/API layer that sits on top of VSN-1. It is not part of the VSN-1 binary protocol specification. It introduces no record type, no field, no identifier, and no requirement. Where it describes behaviour defined by the protocol, the normative specification is authoritative.

03

Architecture and layering

VSN-1 and the VSN Library are distinct layers. The Library implements the protocol; it does not extend, redefine, or negotiate it.

layering
VSN-1        = canonical file / container protocol
VSN Library   = implementation + API layer operating on VSN-1
Application   = consumer of the Library

Library feature  !=  VSN canonical protocol rule

A conforming Library MAY provide reading, writing, recovery, validation, revision management, content materialization, diff, merge, checkout, restore, storage optimization, indexing, caching, diagnostics, import and export, concurrency control, resource management, and multi-container management. These are Library capabilities, not parts of the format.

The Library MUST NOT cause canonical semantics to depend on anything outside VSN-1 canonical data. Canonical recovery MUST NOT require an index, a cache, a checkpoint, an external database, an external service, an undocumented implementation-private table, a revision outside the accepted state, or an algorithm unavailable to a conforming reader. Derived data MAY be deleted at any time and rebuilt from canonical state.

  • Library APIs are not VSN record types.
  • Library classes and methods are not protocol identifiers.
  • Library indexes and caches are not canonical state.
  • Library storage optimizations are not canonical semantics.
  • Library implementation details do not redefine VSN-1.

04

Container management

A Library MAY create a .vsn, open one, close it, read and write it, inspect container metadata, detect the Container Format Version, detect the Encoding Version, detect the VSN Mode, enumerate records, recover the accepted state, rewrite or repack where permitted, handle an incomplete tail safely, and preserve unknown data during rewrite.

Open and recover are distinct. Open establishes access to the bytes of a container. Recover determines the accepted canonical state according to frozen CommitMarker semantics: the highest-Generation structurally complete and semantically valid marker. A Library MUST NOT infer accepted state from a heuristic such as the latest record, the largest Generation absent a valid marker, file length, a physical offset, a record position, the largest RevisionId, the largest ObjectSerial, an index, a checkpoint, or a cache.

Malformed, truncated, or incomplete data MUST be rejected safely rather than partially accepted. Reopening after an interrupted write recovers the previously accepted state and ignores the incomplete tail.

05

File management

A Library MAY create, read, and modify a logical file; rename and move it; delete it; restore it; represent directories where applicable; and handle PathSnapshot state. It MAY enumerate logical files, find a file by FileId or by path, resolve a path to a FileId and a FileId to its current path, and determine whether a file is PRESENT, DELETED, or a DIRECTORY.

rename / move
Rename / Move changes path state.
It does not create a new FileId.

A PathSnapshot describes path state and is not identity. The Library MUST NOT infer identity from a path or from a content hash. Deletion is expressed through the frozen revision semantics as a tombstone; it is not the physical erasure of historical identity, and a deleted file's identity and history remain intact. Recreating a file at a previously used path does not revive the old FileId.

06

Revision management

A Library MAY create and read revisions, obtain revision history, traverse parent relationships, look up a revision, compare and reconstruct revisions, check out, restore as a new revision, obtain the head, and perform RevisionSet operations. It MAY list all revisions, list the history for a given FileId, traverse parents, find ancestors and a common ancestor, and detect divergent history.

A RevisionId is canonical identity. It is never derived from a hash or a physical location, is immutable and persistent, and is never reused. A revision is never edited in place: restoring an older state creates a new revision or a new accepted state rather than mutating historical revision data. Moving a FileHead changes which revision is current and changes no RevisionId. Revision reconstruction walks the frozen resolution chain:

revision resolution
FileId
  -> RevisionId
  -> ContentRef
  -> ObjectSerial

07

Content and object management

A Library MAY store and read canonical content, materialize content, resolve a ContentRef, read an object by ObjectSerial, verify a declared size, verify a content hash where one is present, resolve object dependencies, reconstruct an object, and validate the object graph. It MAY read an ObjectDescriptor, read representation identity and version, enumerate dependencies, detect missing or cyclic references, determine logical and encoded sizes, and compare two objects.

ObjectSerial is identity. It is not a physical offset, and it is not a hash-derived identity.

Content hashes are verification and acceleration mechanisms, never identity. A hash match MUST NOT resolve canonical identity, and hash collision MUST NOT be treated as content equality. The hash domain remains the frozen logical-content domain: the hash covers logical content, not an object descriptor, container framing, or a representation payload. The Library MUST NOT redefine it.

Because ObjectSerial is container-scoped, it carries no meaning outside the container that assigns it. Compaction MAY move physical bytes without changing any ObjectSerial.

08

Representation management

A Library MAY read the Representation Identity and Representation Version, register a representation, detect support, handle an unsupported representation gracefully, reconstruct a representation, validate representation dependencies, and handle transforms. It MAY inspect a representation payload and validate dependency references.

representation descriptors
ObjectDescriptor
  |-- Representation Identity
  |-- Representation Version
  `-- complete object-specific payload

RepresentationDescriptor
  |-- Representation Identity
  |-- Representation Version
  `-- representation-level metadata

A RepresentationDescriptor is a shared declaration, one per Representation Identity and Version, carrying only representation-level values: 0x0801 Representation Identity, 0x0802 Representation Version, and optional 0x0810 representation-level metadata. The ObjectDescriptor is the per-object structure.

The RepresentationDescriptor does not contain per-object reconstruction data. The Library MUST NOT place an ObjectSerial, per-object operands, per-object source references, an EXTENTS operation program, LITERAL or COPY operations, or any object-specific reconstruction state in a RepresentationDescriptor, and MUST NOT treat 0x0810 as a hidden per-object store. Interpreting an object MUST NOT depend on locating a descriptor; descriptor absence is valid.

0x0502 belongs to the ObjectSection structure and is not a ContentObject field. A Library MUST NOT reinterpret it as a ContentObject record field.

09

DIRECT-1 and EXTENTS-1

Every object payload begins with the universal DR-0 header: the object's own Representation Identity followed by its Representation Version. This header is unconditional and is not conditional on the representation. These are the two currently frozen core representations; the Library documents no others.

DIRECT-1

The Library identifies DIRECT-1, reads its object payload, materializes the logical bytes, and verifies the declared size. The payload is the DR-0 header followed by raw logical content.

EXTENTS-1

The Library identifies EXTENTS-1, parses its canonical operation collection, resolves COPY sources from canonical object content, processes LITERAL data, validates dependencies, detects invalid or cyclic dependencies, and materializes the logical content. The payload is the DR-0 header followed by the canonical operation collection.

A reader that does not support a representation still parses it correctly as an opaque, length-delimited payload, and reports it as unsupported rather than invalid.

10

Transactions and commit

A Library MAY begin a transaction, stage changes, create revisions, create a RevisionSet, validate it, commit it, abort it, detect an incomplete transaction, and recover an interrupted commit.

CommitMarker is the sole acceptance authority.

Library indexes, caches, timestamps, file length, record position, and the notion of a "latest record" must never replace CommitMarker semantics. A staged or complete-but-uncommitted state MUST NOT become visible as accepted canonical state, and an aborted transaction exposes no staged state through the accepted read path. Identity allocated before a failed commit remains permanently consumed, as frozen.

ExpectedRevisionId MAY be used by the Library as a concurrency precondition for an optimistic update, but MUST NOT be persisted as canonical revision data.

11

Recovery

A Library MAY open a damaged or incomplete container, scan canonical records, locate the effective CommitMarker, discard an incomplete tail, ignore uncommitted data, preserve the previously accepted state, detect malformed canonical state, rebuild derived indexes and caches, and recover without any external database or service.

Sequential scan is the normative recovery method. Indexes and checkpoints are acceleration only and are never an input to acceptance. Identity allocation that occurred before a failed commit remains consumed. A reader-local resource refusal is not canonical invalidity: refusing an expensive reconstruction reports a resource condition, and the same container remains canonically valid for a reader with sufficient resources.

canonical recovery chain
.vsn bytes
  -> canonical structure
  -> canonical semantic state
  -> logical file state
  -> logical file bytes

Validation and verification

CanonicalCanonical state structure, accepted state, reference completeness.
SemanticFileId, RevisionId, ObjectSerial, ContentRef, FileHead, presence rules, revision graph, representation agreement, descriptor agreement.

Verification covers framing, lengths, uvarint form, UUIDs, references, ObjectSerial, RevisionId, FileId, content size, representations and their dependencies, hashes, the CommitMarker, and canonical state. Verification unavailability is reported distinctly from a verification mismatch. Integrity verification is not identity.

Diff and comparison

A Library MAY compare file against file, revision against revision, revision against workspace state, workspace state against accepted state, and content against content. It MAY produce metadata and path diffs and analyse revision relationships.

A Library MAY diff at file level (created, deleted, modified, renamed, moved, unchanged), revision level (added, deleted, modified, renamed or moved, unchanged files), content level (byte, range, and logical comparison), object level (shared ObjectSerials, new ObjectSerials, changed representation, dependency differences), and metadata level (path, revision, head, representation metadata).

Diff artifacts are derived and disposable. They are never canonical state and never a canonical recovery dependency.

Diff output is a Library-derived result. It does not redefine VSN identity.

Merge

Where the revision graph supports multiple parents, a Library MAY compare revisions, identify common ancestry, detect conflicting changes, produce merged logical content, report conflicts for resolution, and commit the result as a new revision preserving both parent RevisionIds. It MAY locate the merge base, perform a three-way merge, and validate the merged canonical state.

A merge always creates a new revision. It never modifies an existing one, and it does not redefine VSN revision semantics.

Checkout, snapshot, and restore

A Library MAY check out a revision or a RevisionSet, restore a file, a revision, or workspace state, snapshot the accepted state, preview a restore, detect conflicts, and materialize safely.

Restoring content normally creates the appropriate new canonical state rather than mutating an immutable revision. Checkout and materialization are Library operations and change no historical revision.

Import and export

A Library MAY import ordinary files, export revisions and snapshots, clone or copy containers, migrate compatible representations, verify exported content, and stream import and export. Any conversion MUST preserve the canonical semantics required by VSN-1.

Import MUST NOT synthesize identity from external content, and export MUST NOT discard canonical history that a destination model cannot express. External files, an external filesystem, and external databases are never required for canonical reconstruction of a .vsn container.

Streaming and large files

A Library MAY provide streaming reads, streaming writes, incremental materialization, large-object handling, bounded-memory operation, and partial diagnostic inspection. Correctness MUST NOT depend on loading an entire container or an entire object into memory.

Streaming is an API and implementation concern. It does not alter canonical semantics, and a streamed read MUST produce the same logical bytes as a buffered read.

18

Storage Policies

Storage Policy in Container

The storage policy is stored directly in the container as a REC_STORAGE_POLICY record (0x0009) with field ID FID_STORAGE_POLICY (0x0901) and a single byte value (1-4). The four profiles do not appear as wire-mode identifiers.

hierarchy
VSN Protocol
  |
  +-- Storage Policy (in binary, REC_STORAGE_POLICY)
  |       Value: 1 (HIGHLY_VERTICAL), 2 (VERTICAL), 3 (HORIZONTAL), 4 (HIGHLY_HORIZONTAL)
  |
  +-- 
  |       
  |       
  |
  +-- Optimization Configuration (resource parameters)
          search_budget, memory_limit, depth, etc.

HIGHLY_VERTICAL

Value: 1. Purpose: Maximum storage-efficiency effort within explicit resource and safety limits.

  • Aggressive deduplication, content sharing, revision-to-revision reuse
  • Chunked representations, EXTENTS-1 permitted
  • Deep dependency structures allowed with limits
  • Expensive similarity search within budget

VERTICAL

Value: 2. Purpose: High storage efficiency with more bounded optimization. Deduplication and content sharing are preferred but bounded; EXTENTS-1 permitted with depth limits.

  • Deduplication, content sharing preferred but bounded
  • EXTENTS-1 permitted with depth limits
  • Bounded similarity analysis; full-copy fallback common

HORIZONTAL

Value: 3. Purpose: Prefer straightforward representations with limited reuse.

  • Complete content objects preferred; basic deduplication permitted
  • Limited/shallow EXTENTS only if permitted by ENTERPRISE frozen semantics
  • Avoid deep dependency chains and expensive similarity analysis

HIGHLY_HORIZONTAL

Value: 4. Purpose: Maximum straightforwardness.

  • DIRECT-1 required for emitted content; EXTENTS-1 forbidden
  • Reconstruction dependencies forbidden; each object contains complete logical content
  • Exact whole-object reuse MAY still be used where identity semantics allow

Storage-policy profiles do not appear in the container binary. A container has exactly one ModeDeclaration (GR-38); changing writer policy does not change the ModeDeclaration.

Physical storage management

A Library MAY compact, repack, compress, optimize layout, share objects, deduplicate, rebuild indexes and caches, and report storage statistics.

storage layers
Canonical data
  !=
Derived acceleration / storage structures

Compaction MAY change physical layout but MUST NOT change canonical identity semantics. ObjectSerial, RevisionId, and FileId never become physical offsets. Storage reporting SHOULD distinguish canonical storage, derived storage, indexes, caches, checkpoints, and temporary workspace.

21

Garbage collection

A Library MAY identify unreachable objects, identify obsolete derived data, purge safely, compact storage, preserve retained revisions, and preserve canonical reconstruction.

Garbage collection MUST NOT delete content still required by a retained or addressable revision.

The Library MUST NOT delete canonical data merely because a temporary cache or index does not reference it. Where a representation requires reconstruction from other canonical objects, those sources remain canonical data and are not collectable derived data.

22

Integrity and security

A Library MAY verify hashes, verify sizes, detect corruption, handle malformed input, apply resource limits, guard against decompression and resource amplification, enforce path safety, materialize safely, and handle hostile containers.

Hashes are verification and acceleration mechanisms, not identity.

Integrity verification confirms or denies that content matches a recorded value; it never substitutes for FileId, RevisionId, or ObjectSerial. This page defines no signature mechanism: cryptographic signatures are an extension question, not part of VSN-1. A Library MUST reject unsafe output paths during materialization and MUST treat a hostile container as invalid input rather than trusting declared sizes or lengths.

23

Forward compatibility

A Library MAY handle unknown records, unknown fields, unknown extensions, unsupported representations, unsupported transforms, reserved values, and future versions. It skips an unknown field or record by its declared length and preserves it on rewrite where the frozen protocol requires preservation.

independent capabilities
reading support   != writing support
materialization  != safe rewrite / preservation
preserving data  != semantically editing data

A Library MUST distinguish cannot interpret from data is invalid: an unknown but well-formed record is a forward-compatibility situation, while a malformed one is an error. A Library may be able to preserve a structure it cannot semantically interpret, and MUST NOT silently delete data written by a newer implementation.

Concurrency and transaction isolation

A Library MAY admit multiple readers, hold an exclusive writer, use file locking, detect a concurrent writer, detect a stale writer, apply an ExpectedRevisionId precondition, provide transaction isolation, and support safe concurrent access. It MAY provide transaction-local state, a read snapshot, staged changes, atomic multi-file commit, conflict detection, commit retry, abort without exposing staged state, and crash-safe cleanup.

ExpectedRevisionId is a protocol precondition and is never persisted as canonical data.

Concurrency control is Library and API behaviour. It introduces no VSN identity mechanism and does not alter acceptance, which remains with the CommitMarker alone. Uncommitted transaction state MUST NOT be presented as accepted VSN state.

Resource and safety limits

A Library MAY impose configurable controls: maximum object size, maximum reconstruction depth, maximum dependency count, maximum transaction size, maximum memory usage, maximum decompression expansion, execution time limits, and cancellation.

A reader refusing a resource requirement is a Library decision. It does not mean the container is canonically invalid.

The same bytes remain recoverable by a reader with sufficient resources. Resource limits bound this implementation's work; they never redefine canonical validity.

Format-preserving rewrite

A Library MAY rewrite a .vsn while preserving canonical semantics, unknown fields, unknown records, extensions, identities, revisions, representations, and required compatibility information. Derived indexes and caches may be regenerated afterwards.

Rewrite modeMeaning
PreserveCanonicalRewrite while preserving canonical semantics exactly.
PreserveUnknownDataAdditionally preserve data this Library does not understand where VSN-1 requires preservation.
NormalizeProduce an equivalent canonical representation according to the specification.
CompactChange physical layout while preserving canonical semantics.

No mode may change FileId, RevisionId, or ObjectSerial semantics, and none may remove canonical history or accepted state.

Multi-container management

A Library MAY open multiple .vsn containers, compare containers, copy revisions, synchronize or copy content, verify relationships, migrate content, and maintain library collections or catalogs. It MAY mount and unmount containers, discover them, query container metadata, and search across containers.

These are Library and application facilities, not new VSN protocol semantics. Because ObjectSerial is container-scoped, a cross-container operation MUST NOT assume that an ObjectSerial from one container identifies the same object in another; content is re-established through canonical content and identity allocation in the destination container.

Capability and compatibility queries

A Library MAY expose the supported VSN version, Encoding Version, modes, representations, representation versions, transforms, hash algorithms, extensions, and resource limits. It MAY answer, for a given container, whether it can read, recover, materialize, edit, write, or preserve unknown data.

These queries report existing Library behaviour. They MUST NOT invent new protocol registry entries merely for API reporting.

The capabilities are independent: the ability to read a container does not imply the ability to rewrite it safely, the ability to identify a representation does not imply the ability to materialize it, and the ability to preserve unknown data does not imply the ability to edit it semantically.

Diagnostics and developer APIs

A Library MAY inspect a container, a record, an object, the revision graph, the dependency graph, the recovery state, and a representation; explain a validation failure; support conformance testing and test-vector verification; and report statistics. It MAY offer explanatory operations for a recovery result, a revision, an object, a representation, a dependency graph, a validation failure, or a commit.

diagnostic resolution chain

  -> RevisionId

These are diagnostic and implementation facilities. They MUST NOT become canonical recovery dependencies. Diagnostic information is derived information and is not canonical identity; a diagnostic byte offset is a diagnostic location only and never participates in canonical resolution.

Implementation status

No VSN Library implementation exists in this repository.

This repository contains the BRP-1 and VSN-1 specification and its generated documentation. Every capability on this page is an intended capability or a Library facility, described so that a conforming implementation has a clear contract. Nothing here asserts that an implementation exists, that a conformance suite has been executed, or that a byte-level test vector has been verified by running code.

The normative specification, its frozen rules, and its frozen byte vectors are described in the protocol specification. This page documents only the implementation and API layer above them.
